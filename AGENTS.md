# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install            # also fetches the Claude Code binary bundled with the Agent SDK (~200 MB)
npm run typecheck      # tsc -p . (noEmit); the only static check, there is no linter or formatter
npm test               # node --test "test/*.test.ts"
node --test test/control.test.ts                      # one file
node --test --test-name-pattern="continue" test/control.test.ts   # one test
```

`test/browser.test.ts` drives the dashboard in headless Chrome. It looks at `PI_FUSION_CHROME`, then the usual install paths for the platform, then any Chromium name on `PATH`, and skips itself when it finds none.

## Architecture

A single Pi extension. `extensions/fusion.ts` default-exports `fusion(pi: ExtensionAPI, options?: FusionOptions)`, which registers the `fusion` and `fusion_control` tools, the compatibility `claude` and `claude_control` pair, the `/fusion` command, a renderer for `pi-fusion-run` messages, and the `session_shutdown` and `session_before_tree` handlers. Everything else is a module it imports.

Each delegation call starts a **child**: a headless coding session in the host's working directory. Which harness runs it is the **backend**: `claude`, run through `@anthropic-ai/claude-agent-sdk`, is the only one this build runs. `pi` is a name records, routing, role capabilities and the `backend` parameter all know, and every call routed there is refused before a handle is taken or a child starts; `FusionOptions.backends` is how a test injects one, and nothing reads a backend from the user; a backend must be registered under its own name, and a registration whose key and `name` disagree is refused at load, before a session could be mapped or a run tagged with the wrong one. The role (`plan`, `implement`, `ultracode`, `ask`, and `security`, which no backend runs here) fixes the child's model, effort, tool list, permission mode and contract; `ROLES` in `fusion.ts` holds the Claude table, `extensions/roles.ts` holds the capabilities every backend shares, and each role's behavior is prose in `contracts/*.md`, appended to the child's system prompt. Change how a role behaves by editing its contract, not the code. The extension throws at load if a contract file is missing. `contracts/plan.md`, `contracts/implement.md`, `contracts/ask-answer.md` and `contracts/ask-review.md` are prose any backend's child can run: they name no vendor, no model and no harness's own tool names, and they speak of a shell tool, search tools and file-editing tools instead. `contracts/ultracode.md` is Claude's alone and names what it needs to.

A Pi child of this extension is itself a Pi session, so it loads this extension too. `piLaunch` sets `PI_FUSION_CHILD=pi` in a child's environment, and `fusion()` registers nothing at all when it sees that value, before it validates a contract or registers a tool: a child cannot delegate again. It is an internal marker rather than a user knob — nothing documents it, no other value means anything to it, and only a Pi launch ever sets it.

The SDK lives behind a backend boundary. `fusion.ts` owns the run lifecycle and imports no SDK: it asks `claudeBackend` in `extensions/backends/claude.ts` to run a child and reads the run back through the records in `extensions/backends/types.ts`. Those types name no SDK, and the role and session shapes a backend takes stay its own, through their generic parameters. Keep it that way: SDK options, the questions bridge and stream handling belong in the backend, and process launching and descendant killing in `extensions/process-tree.ts`, which takes its own launch shape so no SDK type reaches it.

A record is tagged with the backend that wrote it, and each backend's identity is its own. A Claude entry keeps the flat `sessionId` and `checkpoint` it always had. A Pi entry keeps a structured `session` reference — session id, session file and, when one is trusted, a checkpoint — and the `selection` the child actually ran with, because a Pi continuation repeats that selection rather than resolving a model again. An entry with no backend is a Claude run, which is what everything written before the tags is. A record this host cannot read keeps its handle and is refused rather than continued.

Run state lives in two places, and the difference matters:

- **In memory**, for this Pi process: `LiveRun` records in `fusion.ts` and the dashboard's `RunStore`. They die with the process unless `PI_FUSION_HISTORY=1` mirrors them to disk through `history.ts`.
- **In the host session transcript**, as `pi-fusion` custom entries appended with `pi.appendEntry`. Each carries the handle, role, Claude Code session id and a checkpoint (the uuid of the child's last assistant message). `runRecords(branch)` reads the last entry per handle on the host's current branch, which is why resuming, `/tree` and forking a host session carry the runs with them. A forked host resumes the recorded session with `--fork-session` on first use.

Invariants worth knowing before changing run handling: at most one run that can change files is active at a time, across backends (`ask` runs may run alongside); a question blocks its child until exactly one answer arrives, from the host or the user; `/tree` is refused while any run is unfinished, because a late report or entry would land on the wrong branch; what a finished run records is decided from its outcome alone, by `recordDecision`, and an outcome naming a session the run cannot have had fails the run and writes nothing at all.

The dashboard page is deliberately plain: no framework, no inline script or style, no `innerHTML`, `eval` or `new Function`, no `url()` or `@import` in the CSS. `test/dashboard.test.ts` asserts all of that statically, so keep DOM building node by node.

## Tests

The suite never runs a real child of any backend, and never a paid one. Three fakes do that work, and no two of them are interchangeable: `test/fake-claude.mjs` for the Claude backend's protocol, `test/fake-pi-backend.ts` for the shared lifecycle, and `test/fake-pi.mjs` for the native RPC protocol a Pi child speaks. Two of the three are real subprocesses and one is not: `test/fake-claude.mjs` is started by the real Claude Agent SDK's own `query`, with the fake named in place of the Claude Code binary, and `test/fake-pi.mjs` is launched by this suite's own composition and imports node builtins alone, with no SDK inside that program. `test/fake-pi-backend.ts` is the in-memory one, and it starts no process at all.

`test/fake-pi-backend.ts` is a scripted in-memory backend injected through `fusion(api, { backends })`. It runs no process, speaks no protocol and reads no configuration: a script says what each run reports, and the start it captures gives the test the role and intent the host handed over, a steer channel, a question channel, a gate that holds a pending run and an abort response. `test/lifecycle.test.ts` drives the registered tools, the host branch, the history and the controls against it, for both a `pi`-named and a `claude`-named backend. It proves what Fusion does with a backend's answers and nothing about Pi itself; Pi's own session semantics stay `test/spikes/pi-session-lifecycle.mjs`'s to measure against a real child.

`test/fake-pi.mjs` is the third, and the Pi one of the two that are processes: it writes the bootstrap's own stage diagnostics on stderr and speaks the native RPC protocol on stdout and stdin out of literals, importing two node builtins and nothing else — no SDK, no model runtime, no provider, and nothing that starts anything. `test/pi-transport.test.ts` drives `extensions/backends/pi-transport.ts` against it through the production storage, input and launch composition, with that file named as the bootstrap through the same internal seam a real child would take, and each case under a root of its own with a built-up environment and `test/sdk-fence.mjs` preloaded. What it exercises is this host's own reading of the protocol; it is no evidence about Pi, and the transport it drives is registered nowhere. The rule the default suite keeps is unchanged by it: no test here builds a real Pi session or model runtime, reaches a real backend executable, or sends a model inference request. The Claude cases do build the Claude SDK's own real objects around the fake binary, which is what makes that half a protocol test at all. The fence and the two calls in `test/pi-bootstrap.test.ts` that run without it — one reading the installed package's exports through the bootstrap's own compatibility check, the other calling the public `getAgentDir()` accessor — are that file's own and are untouched here, and a test still asserts there are exactly two of them.

`test/pi-question-routing.test.ts` is none of the three: it drives `extensions/backends/pi-question-routing.ts` against scripted in-memory doubles of its own — one child whose `respond` answers out of a literal script and one ask that is a deferred — with no process, no protocol, no SDK and no fake behind them, so it measures this host's own arbitration of a dialog and says nothing about how a real child opens or reads one.

`test/pi-prepare.test.ts` is the same kind: it drives `extensions/backends/pi-prepare.ts` against a scripted start seam and a scripted child of its own — per-command answer queues, a deferred exit and a shutdown that reports or throws — with the real call storage prepared under a root each case owns and removes. That storage is the production one and not a stub, so what each case touches outside memory is the whole layout `prepareCallStorage` makes — the owned directories, an empty catalog store published into place, the per-call directory and its compiler caches — and then the call input this composition writes into it. No child, process, protocol, session, model runtime, provider or SDK is behind any of it.

`test/pi-task.test.ts` is the same kind again and thinner still: it drives `extensions/backends/pi-task.ts` against scripted in-memory doubles of its own — one child that answers out of per-command queues and whose turn and shutdown the case controls, a prepared child that is an object literal, a question watch that is a deferred, and events written out as literals — with no process, protocol, storage, SDK or fake behind any of it, and no root or file of its own. Its eight cases are the happy turn and its counting, the leaf gates at both ends, the steer queue's own delivery accounting, the refusals a settled turn's own records earn — the mark before the prompt and the freeze at the close among them — every turn end under its own name and a child that had already gone, a fatal question, cancellation, and the strict readbacks with a cleanup that failed and an observer that could not be read. What it measures is this host's own order, gate, accounting and single shutdown; nothing in it says how a real child streams a record, moves a leaf or counts its usage.

`test/pi-outcome.test.ts` is the same kind and the thinnest of them: it drives `extensions/backends/pi-outcome.ts` against object literals alone — the exit reports, refusals, task results and streamed records are typed out in that file — with no process, protocol, storage, session, model runtime, SDK or fake behind any of it and no root or file of its own, and it imports two functions from the host for one thing each: `recordDecision`, for what the record layer then does with a run this mapping produced, and `failureMessage`, for what a person is actually shown for one, which for a cancelled run is its activity line and nothing else. Its seven cases are the session table with every reference it refuses, every concern individually, together and in order with the nested restore and the foreign seam among them, every reason of every stage mapped with markers planted in each kept value proving none of them reaches a message, a turn that finished with its accounting and its cleared context fields, the demotion of a turn whose child would not let go and the record decision each intent then gets, every other ending with the live counts it preserves, and the progress mapper's window, its caps and emitters that throw. What it measures is this host's own mapping; nothing in it says how a real Pi child ends, cleans up or streams a record, and no user-facing behavior exists to document yet because nothing constructs this module.

Measurements against a real Pi child, and against the installed SDK's own runtime, live under `test/spikes/`, outside the glob, and are run by hand. `test/spikes/pi-config-writes.mjs` has two stages: `--stage historical`, the research-stage cases that compared ways of starting a child, and `--stage impl`, which drives the production bootstrap, launch options and storage layout against real children. Its three fixture scripts are manual-harness-only. `test/spikes/pi-fetch-guard.mjs` is a `NODE_OPTIONS` preload that wraps `globalThis.fetch` in the fixture processes it is loaded into: it records each call, rejects any origin the fixture does not own, and never lets a redirect be followed automatically. That is all it covers — not a raw socket, not another client, not a subprocess of the child. `test/spikes/pi-helper-interposer.mjs` is a second preload, loaded **after** that guard and never instead of it, for the `P7` helper-download cases alone: it captures the already guarded `fetch` and rewrites an exact list of urls — the release page and the asset url the SDK's own tool manager asks for, per helper — to one loopback listener the harness owns, leaving every other url to reach the guard and be refused there. It is a url map validated from three fixture-only variables, not a proxy, a sandbox or a network boundary: the two calls it exists for are bodiless GETs, a mapped call it could not rebuild without losing what it carried is refused rather than sent, and a configuration it cannot validate throws instead of installing. `test/spikes/pi-storage-caller.mjs` is a controller that calls the production helpers and launches one child, standing in for a transport rather than being one: nothing it measured — a real child's startup, its configuration writes, the OAuth rotation or the helper acquisition — exercises or qualifies `extensions/backends/pi-transport.ts`, and those measurements keep the scope they were made in. None of them is imported by a test, and a claim from one of them is a manual measurement, never a suite result. `test/spikes/pi-auth.mjs` is another manual harness, with `test/spikes/pi-auth-driver.mjs` as its SDK process: it measures the credential store the production storage selects — rotation, an overlap on one shared file, a failed refresh, a missing auth file, malformed and unknown shapes, and a version skew behind `--package` — against a throwaway profile of literal dummy credentials and a loopback token endpoint. It builds no session, runs no model request and speaks no protocol, so it measures the installed SDK's own runtime rather than a real child. Inside a driver the SDK's credential store is what reads and rotates the shared `auth.json`, through the public API, and that is the behavior under measurement; the driver's own observation code never reads its bytes, and the controller snapshots that file only while no driver is running. Its one `C1` control is not a case and is counted apart: it points the driver at a generated fake package with the test-only fence preloaded, and proves a foreign constructor failure is recorded as evidence without its text, name, code, cause or stack reaching a stream or a record. The `P6` group inside `--stage impl` is the bootstrap half of the same auth question, and it is a real child rather than a store driver: one fixture OAuth provider the call names as an ordinary resource, one loopback token endpoint per case, and three cases — a rotation that writes the user's own file back once and reaches the model with only the credential it minted, a refresh that can never mint, and a malformed credential file the bootstrap refuses at its models stage. The `P5` group inside `--stage impl` is the first one that names resources, and its input-refusal cases add two fixture-side controls of their own: the test-only `test/sdk-fence.mjs`, preloaded beside the fetch guard so a preflight that stopped refusing a specifier would find no backend SDK to import, and runtime-generated `npm` and `git` shims on the front of the child's `PATH` that log and exit 86 without running anything. Both reach only that far — a module-resolution rule in the processes preloaded into, and the two commands a package install resolves through `PATH` — and neither is a sandbox.

`test/sdk-fence.mjs` is test-only and production never sees it. `test/pi-bootstrap.test.ts` starts each of its subprocesses with node's own `--import` pointing at it, and a resolve hook there refuses a backend SDK by name, by subpath or by a resolved url inside one of those installed packages, so a bootstrap rule that stopped holding cannot let a child of that file reach a real package instead of failing. Each such subprocess also gets a sanitized environment and its own working directory, home, temporary and cache directories under one root the test makes and removes. Two calls in that file run without the fence and are named there: one reads the installed package's exports through the bootstrap's own compatibility check, the other calls the public `getAgentDir()` accessor. Neither builds a session, a settings manager, a model runtime or a backend, and a test asserts there are exactly two of them. What this is not: it is a module-resolution rule rather than a sandbox or a network boundary, it says nothing about other test files, and the owned directories retarget the usual variables rather than confining every write a process could make.

The suite never runs the real Claude Code binary. `test/fake-claude.mjs` speaks the SDK's side of the stream-json protocol: it answers the `initialize` control request, reads the prompt from the `user` line, then plays the scenario named by `FAKE_CLAUDE_SCENARIO` (`ok`, `read`, `question`, `two-questions`, `steer`, `error`, `denied`, `wind-down`, `big-context` and others in that file). Tests point the SDK at it with `PI_FUSION_CLAUDE_BIN`. Set `FAKE_CLAUDE_LOG` to a path to see what the SDK writes to the fake's stdin. Add a scenario there rather than mocking the SDK.

## Conventions

- TypeScript with `allowImportingTsExtensions`: relative imports carry the `.ts` extension (`./review.ts`).
- Tabs for indentation, semicolons, long lines. Comments are `/** ... */` above a declaration and say why it is the way it is, not what the code does.
- `CONTEXT.md` fixes the vocabulary: host, child, role, run, handle, question, waiting, answer, handoff, escalation, steer, review run, history. Each term lists the words to avoid. Use these words in code, prose and tool messages.
- User-facing behavior is documented in `README.md` (overview) and `docs/*.md` (one page per topic). A change that alters what a tool, a variable or the dashboard does belongs in the matching page in the same commit.

## Commit Messages
- Keep messages short and concise. Prefer a single-line subject up to ~150 characters describing the change in the imperative ("add X", "fix Y"). Add a brief body only when the *why* isn't obvious from the diff.
- Do **not** add `Co-Authored-By` or any AI/Claude contribution trailers to commit messages.
