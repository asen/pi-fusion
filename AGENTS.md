# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install            # also fetches the Claude Code binary bundled with the Agent SDK (~200 MB)
npm run typecheck      # tsc -p . (noEmit); the only static check, there is no linter or formatter
npm test               # node --test --test-timeout=60000 "test/*.test.ts"; a test past 60 s is cancelled and named
node --test test/control.test.ts                      # one file
node --test --test-name-pattern="continue" test/control.test.ts   # one test
```

`test/browser.test.ts` drives the dashboard in headless Chrome. It looks at `PI_FUSION_CHROME`, then the usual install paths for the platform, then any Chromium name on `PATH`, and skips itself when it finds none.

## Architecture

A single Pi extension. `extensions/fusion.ts` default-exports `fusion(pi: ExtensionAPI, options?: FusionOptions)`, which registers the `fusion` and `fusion_control` tools, the compatibility `claude` and `claude_control` pair, the `fusion_activate` and `fusion_deactivate` mode tools, the `/fusion` command, a renderer for `pi-fusion-run` messages, and the `session_start`, `session_shutdown` and `session_before_tree` handlers. Everything else is a module it imports.

Fusion starts off in every extension instance: `enabled` is the one mode state, and the first entry point that finds the host's tool list bound — `session_start`, or the first command or tool call on a host that emits none — hides the four workflow tools and leaves `fusion_activate` active, saving the workflow subset Pi had active for the first on. `turnOn` and `turnOff` are the one implementation `/fusion on` and `off` and the two mode tools share, each a synchronous step with no await in it: off takes the unfinished-run check `switchTo` uses, and only the mode tool that leaves the current mode is ever active, added only when `getAllTools()` offers it, so an allow list or exclusion is never bypassed. The workflow guidance rides on the workflow tools and leaves the prompt with them; the mode tools carry only their own guidance, which restricts them to an explicit request for Fusion. Nothing persists the mode.

Each delegation call starts a **child**: a headless coding session in the host's working directory. Which harness runs it is the **backend**: `claude`, run through `@anthropic-ai/claude-agent-sdk`, and `pi`, run through this build's own composition of the public Pi SDK in `extensions/backends/pi-*`. `fusion()` registers both, with a host's own `FusionOptions.backends` entries merged over them; no user configuration reaches that option — the `backend` parameter a tool call carries is user-visible, but it picks among what is already registered and registers nothing — so taking a registration back out again is a code change rather than a runtime switch. Which backend a fresh run goes to, and the model and effort it binds there, is the session's **configuration** (`Configuration` in `fusion.ts`, the pure settings in `extensions/profiles.ts`, the file in `extensions/profile-store.ts`): each role is enabled or not and names a backend, a model and an effort. The built-in configuration is the legacy behavior — every role enabled, `security` on `pi` and every other role on `claude`, models and efforts from the role variables — captured once per extension instance; a named profile replaces it, loaded from `<agent dir>/pi-fusion/profiles.json` as the default by a `session_start` that every call and command waits for, or by `/fusion profile use`. A call that leaves the `backend` parameter unset goes to the role's configured backend; a call naming the other backend runs there on that backend's captured legacy defaults, never on the settings configured for the role's other backend; a disabled role is refused for a fresh run and a continuation alike, through both tools, before a handle is taken; and a continuation stays on the backend its record names, `pi` included, whether or not the call names one; `pi` runs `plan`, `implement`, `ask` and `security` there, on the user's own Pi provider configuration: a pi call takes a provider and model id from the call's `model` parameter or from `PI_FUSION_PI_<ROLE>_MODEL`, and a call that carries neither is refused by the binding before that backend is asked for a session, a control or a run. A backend this build knows and a host registered nothing for is still a name records, routing, role capabilities and the `backend` parameter all know, and every call routed there is refused with what happened before a handle is taken or a child starts; a backend must be registered under its own name, and a registration whose key and `name` disagree is refused at load, before a session could be mapped or a run tagged with the wrong one. The role (`plan`, `implement`, `ultracode`, which is Claude's alone, `ask`, and `security`, which is Pi's alone) fixes the child's model, effort, tool list, permission mode and contract; `security` is the one role the compatibility `claude` tool does not advertise at all, so that tool refuses the name rather than refusing a capability it never offered, and it is the one role the host is told to use only when the user asks for a security investigation, audit or fix; `ROLES` in `fusion.ts` holds the Claude roles' tools, permission modes and contracts — their model and effort are the configuration's, resolved per call — `extensions/backends/pi-binding.ts` resolves what a Pi role runs as from the call, the recorded selection and the fallback the route hands it, `extensions/roles.ts` holds the capabilities every backend shares, and each role's behavior is prose in `contracts/*.md`, appended to the child's system prompt. Change how a role behaves by editing its contract, not the code. The extension throws at load if a contract file is missing, and that check is the union of both bindings' contracts: the Claude table's, the ask modes' and `PI_CONTRACT_FILES` from the Pi binding, so a contract only a Pi role names is as much a broken install as one a Claude role names. `contracts/plan.md`, `contracts/implement.md`, `contracts/ask-answer.md` and `contracts/ask-review.md` are prose any backend's child can run: they name no vendor, no model and no harness's own tool names, and they speak of a shell tool, search tools and file-editing tools instead. `contracts/ultracode.md` is Claude's alone and names what it needs to. `contracts/security.md` is Pi's alone, for the same reason the other way round, and is written in the same vendor-neutral prose: it says the task is where the authorization to change application code comes from, that a finding carries a severity and whether it is confirmed or inferred, and that no secret goes into a report by value.

A Pi child of this extension is itself a Pi session, so it loads this extension too. `piLaunch` sets `PI_FUSION_CHILD=pi` in a child's environment, and `fusion()` registers nothing at all when it sees that value, before it validates a contract or registers a tool: a child cannot delegate again. It is an internal marker rather than a user knob — nothing documents it, no other value means anything to it, and only a Pi launch ever sets it.

What `fusion()` does at load, in this order because each step is cheaper than the next: the child marker, the contract files, the existence of `extensions/backends/pi-bootstrap.mjs` — the one program every Pi child is launched by — and then the registration of both backends. A missing contract and a missing child program are each a refusal of this extension's own, rather than a call that finds out once a child is already being started. No host module imports that program: the two constants both ends of the wire agree on — the startup exit code `78` and the `pi-fusion-bootstrap` diagnostic marker — live in `extensions/backends/pi-bootstrap-protocol.mjs`, which imports nothing, and the child's program imports and re-exports them from there. That is what leaves the existence check a refusal of its own: this host no longer depends on the child's entry module and never evaluates it, so an install missing that program gets this loader's own fixed refusal rather than node's module error before a line of this ran. It says nothing about what the split keeps out of this process — `pi-control-extension.mjs` reaches the host through `pi-session-restore.ts` and `pi-question-tool.mjs`, with `typebox` behind it, through `pi-launch.ts`, so beyond the modules the host needs anyway the only one it spares is the child-only `pi-helper-retry.mjs`, and the public SDK is loaded inside the child's own program when that program runs. An install missing one of this host's own sources, the protocol module included, still fails that way and cannot load this extension at all.

The SDK lives behind a backend boundary. `fusion.ts` owns the run lifecycle and imports no SDK: it asks `claudeBackend` in `extensions/backends/claude.ts`, or the Pi backend `createPiBackend()` composes in `extensions/backends/pi-backend.ts`, to run a child and reads the run back through the records in `extensions/backends/types.ts`. Pi's own half imports no SDK anywhere in this process either — the public SDK is loaded by the child's program alone. Those types name no SDK, and the role and session shapes a backend takes stay its own, through their generic parameters. Keep it that way: SDK options, the questions bridge and stream handling belong in the backend, and process launching and descendant killing in `extensions/process-tree.ts`, which takes its own launch shape so no SDK type reaches it.

A record is tagged with the backend that wrote it, and each backend's identity is its own. A Claude entry keeps the flat `sessionId` and `checkpoint` it always had, and the flat `model` and `effort` the run was admitted with, defaults included, which is what a later call to that handle stays on whatever profile is selected since, and a cap handoff from it keeps the model of; an older entry that kept no model or no effort continues on the legacy defaults this instance captured, never on the current profile, and says so. A Pi entry keeps a structured `session` reference — session id, session file and, when one is trusted, a checkpoint — and the `selection` the child actually ran with, because a Pi continuation repeats that selection rather than resolving a model again. An entry with no backend is a Claude run, which is what everything written before the tags is. A record this host cannot read keeps its handle and is refused rather than continued.

Run state lives in two places, and the difference matters:

- **In memory**, for this Pi process: `LiveRun` records in `fusion.ts` and the dashboard's `RunStore`. They die with the process unless `PI_FUSION_HISTORY=1` mirrors them to disk through `history.ts`.
- **In the host session transcript**, as `pi-fusion` custom entries appended with `pi.appendEntry`. Each carries the handle, the role and the session the run ran in: a Claude entry its flat session id and a checkpoint (the uuid of the child's last assistant message), with the flat model and effort beside them, a Pi entry its structured reference and the selection that run resolved to. `runRecords(branch)` reads the last entry per handle on the host's current branch, which is why resuming, `/tree` and forking a host session carry the runs with them. A forked host forks the recorded session on first use, in its backend's own way: a Claude run is resumed with `--fork-session`, while a Pi run is sent Fusion's own fork control command at the recorded checkpoint and the session id and file the child reports back are accepted only after that new session reads back as standing at exactly that entry.

Invariants worth knowing before changing run handling: no run starts while Fusion is off, and off is refused while any run is unfinished, so the hidden control tools never strand a run; at most one run that can change files is active at a time, across backends (`ask` runs may run alongside); applying settings — a profile, `builtin` or the editor's Apply — is refused while any run is unfinished, by the same check `/fusion off` uses, and that check and the assignment, with the tool re-registration that carries the new guidance, are one synchronous step; a run binds its role once, when it is admitted, after the last await before it registers; a question blocks its child until exactly one answer arrives, from the host or the user; `/tree` is refused while any run is unfinished, because a late report or entry would land on the wrong branch; what a finished run records is decided from its outcome alone, by `recordDecision`, and an outcome naming a session the run cannot have had fails the run and writes nothing at all.

The dashboard page is deliberately plain: no framework, no inline script or style, no `innerHTML`, `eval` or `new Function`, no `url()` or `@import` in the CSS. `test/dashboard.test.ts` asserts all of that statically, so keep DOM building node by node.

## Tests

The suite never runs a real child of any backend, never a paid one, and never a line of the Pi backend this build registers — `test/tripwire.ts` stands in its place in every test host but two, and those two take the real registration only to watch the binding refuse a pi call for having no model, before that backend is asked for a session, a control or a run. Three fakes do the rest of that work, and no two of them are interchangeable: `test/fake-claude.mjs` for the Claude backend's protocol, `test/fake-pi-backend.ts` for the shared lifecycle, and `test/fake-pi.mjs` for the native RPC protocol a Pi child speaks. Two of the three are real subprocesses and one is not: `test/fake-claude.mjs` is started by the real Claude Agent SDK's own `query`, with the fake named in place of the Claude Code binary, and `test/fake-pi.mjs` is launched by this suite's own composition and imports node builtins alone, with no SDK inside that program. `test/fake-pi-backend.ts` is the in-memory one, and it starts no process at all.

`test/tripwire.ts` is none of the three and not a fake at all: it is the pi backend the test hosts register in place of the one this build registers by default, in every host but the two that take `productionDefaults()` to read the binding's own refusal. No case of the suite is about running a real Pi child, so each of its entry points — `control`, `session` and `run` — records that it was reached and throws one fixed sentence. The hook that reads those reaches is registered at module level, when a file imports it, rather than inside a case: a case that swallowed the throw — a tool whose error becomes a returned message, a run whose failure becomes a report — would otherwise pass while having reached a backend that in production starts a real Pi child, and this way the whole file fails on it whichever case did it. A host that injects a pi backend of its own spreads it over this one, `{ ...piTripwire(), pi: own }`.

A test host that delegates turns Fusion on the way a user's request does, through the registered `fusion_activate` tool, with `turnOn` and the tool-list accessors of `test/host-tools.ts`; there is no default-on option for a test to pass. `test/profiles.test.ts` holds the mode cases: the startup mask and a direct call it refuses, the tools and the commands making the same change, a refused deactivation for running, waiting and finishing runs, an empty saved subset, an allow list without the mode tools, a host that fails mid-update, a host with no `session_start`, and the guidance each tool carries.

`test/backends.test.ts` pins where the suite registers the extension rather than counting it, through the compiler's own parser: ten registrations — one in `test/control.test.ts`, four in `test/extension.test.ts`, one in `test/lifecycle.test.ts`, one in `test/profiles.test.ts`, two in `test/routing.test.ts` and one in `test/session.test.ts` — each naming `piTripwire` or `productionDefaults` and never both, and exactly two of them, one in `test/extension.test.ts` and one in `test/routing.test.ts`, taking this build's own registration. Those two are the only cases that read the registered pi backend, and what they read is the binding's refusal: every variable a pi role could resolve a model from is deleted first, `productionDefaults()` refuses the registration outright while one is still set, and the explicit pi call is then refused for having no model, before that backend is asked for a session, a control or a run. The same file pins the protocol import boundary: the constants module names no module at all, the transport names it and never `pi-bootstrap.mjs`, no production module of any extension this repository ships imports that program, and `pi-launch.ts` names it as the path it launches — which the compiler's own scanner tells from an import and a pattern over the text would not. `test/extension.test.ts` pins the loader's own order the same way, as a static read of `extensions/fusion.ts` and no more: the child marker, the contracts, the child's program, then the pi registration, each written before the next. Nothing in the suite removes a contract or that program from this repository to watch one throw, so a real install with one of them gone stays a manual check.

`test/fake-pi-backend.ts` is a scripted in-memory backend injected through `fusion(api, { backends })`, over the tripwire. It runs no process, speaks no protocol and reads no configuration: a script says what each run reports, and the start it captures gives the test the role and intent the host handed over, a steer channel, a question channel, a gate that holds a pending run and an abort response. `test/lifecycle.test.ts` drives the registered tools, the host branch, the history and the controls against it, for both a `pi`-named and a `claude`-named backend, the `security` role included: that a `security` call with no backend named runs on `pi` and blocks every other file-changing run on either backend, that it keeps the writer slot while it waits for an answer, that a continuation of it stays on `pi` with its recorded selection and every `claude` route to it is refused, and the reviewer every finished run gets — the session's configured `ask` run, a Claude one in the built-in configuration and a Pi one on its own model and effort under a profile that puts `ask` there, the same reviewer for a `security` run and a Claude `implement` run under `PI_FUSION_AUTO_REVIEW`, a run an earlier Pi process left, a reviewer the settings cannot bind or whose backend is not registered, and none at all while `ask` is disabled. It proves what Fusion does with a backend's answers and nothing about Pi itself; Pi's own session semantics stay `test/spikes/pi-session-lifecycle.mjs`'s to measure against a real child.

Every test host passes a profile store of its own — `memoryProfileStore()` in a registration, and `productionDefaults()` returns one too — so no case reads or writes the user's `profiles.json`. `test/profiles.test.ts` drives the configuration, the store and the commands: the pure validation, the file store under a root each case owns (no write for a missing file, the private directory and file, malformed data left alone, two stores on one path queued, a failed rename that leaves the file and no temporary behind), routing under a configuration as literals, and a host whose fake `registerTool` models the two SDK behaviours this feature depends on — a name registered again replaces its definition, and a refresh under an allow list puts every allowed tool back on the active list. `test/fake-pi.mjs` is the third, and the Pi one of the two that are processes: it writes the bootstrap's own stage diagnostics on stderr and speaks the native RPC protocol on stdout and stdin out of literals, importing two node builtins and nothing else — no SDK, no model runtime, no provider, and nothing that starts anything. `test/pi-transport.test.ts` drives `extensions/backends/pi-transport.ts` against it through the production storage, input and launch composition, with that file named as the bootstrap through the same internal seam a real child would take, and each case under a root of its own with a built-up environment and `test/sdk-fence.mjs` preloaded. `test/pi-outcome.test.ts` is the same kind and the thinnest of them: it drives `extensions/backends/pi-outcome.ts` against object literals alone — the exit reports, refusals, task results and streamed records are typed out in that file — with no process, protocol, storage, session, model runtime, SDK or fake behind any of it and no root or file of its own, and it imports two functions from the host for one thing each: `recordDecision`, for what the record layer then does with a run this mapping produced, and `failureMessage`, for what a person is actually shown for one, which for a cancelled run is its activity line and nothing else. Measurements against a real Pi child, and against the installed SDK's own runtime, live under `test/spikes/`, outside the glob, and are run by hand. `test/spikes/pi-config-writes.mjs` has two stages: `--stage historical`, the research-stage cases that compared ways of starting a child, and `--stage impl`, which drives the production bootstrap, launch options and storage layout against real children. ## Conventions

- TypeScript with `allowImportingTsExtensions`: relative imports carry the `.ts` extension (`./review.ts`).
- Tabs for indentation, semicolons, long lines. Comments are `/** ... */` above a declaration and say why it is the way it is, not what the code does.
- `CONTEXT.md` fixes the vocabulary: host, child, role, run, handle, question, waiting, answer, handoff, escalation, steer, review run, history. Each term lists the words to avoid. Use these words in code, prose and tool messages.
- User-facing behavior is documented in `README.md` (overview) and `docs/*.md` (one page per topic). A change that alters what a tool, a variable or the dashboard does belongs in the matching page in the same commit.

## Commit Messages
- Keep messages short and concise. Prefer a single-line subject up to ~150 characters describing the change in the imperative ("add X", "fix Y"). Add a brief body only when the *why* isn't obvious from the diff.
- Do **not** add `Co-Authored-By` or any AI/Claude contribution trailers to commit messages.
