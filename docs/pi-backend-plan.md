# Plan: a Pi backend for Fusion

Status: in implementation. Step 1 is complete, and step 2 has landed: the backend boundary and the process-tree helper are extracted, with every Claude behavior and test unchanged. Steps 3 to 6 are still a proposal, and nothing Pi-specific runs yet. Agreed scope: generic Fusion tools with Claude compatibility, supporting `plan`, `implement`, and `ask` on Pi, with `ultracode` remaining Claude-only. A Pi-only `security` role is a full coding role and occupies the single active file-changing run slot.

The child's execution shape is decided: a separate process that builds a Pi runtime from the installed package's public SDK exports and serves the real RPC mode, rather than the stock CLI. Both spikes this plan depended on are complete: [docs/pi-config-write-spike.md](pi-config-write-spike.md) measured that choice, and [docs/pi-session-lifecycle-spike.md](pi-session-lifecycle-spike.md) measured the session lifecycle it depends on, against Pi 0.85.1 with a deterministic loopback model fixture. Findings quoted here are marked measured (one of those spikes ran it), source (read in the installed Pi 0.85.1, not executed) or untested (neither). The session semantics below are no longer proposals waiting on a measurement, except where this document says a decision is still pending.

## Outcome

The host can run a child through either Claude Code or Pi, with the same handles, background work, questions, controls, dashboard, and durable continuation. Pi uses the user's working provider configuration, including DeepSeek; Fusion does not implement a provider API client.

Backend and role are independent. A backend chooses the execution harness; a role chooses the task contract, available tools, and model in its backend binding. The Pi backend is provider-neutral and contains no DeepSeek-specific defaults or routing. Backend selection follows the requested backend, the continued run, or the role's supported backends; a child's refusal never triggers automatic backend switching.

## Role capabilities and backend support

Define roles separately from backend implementations, with explicit supported backends, required tool capabilities, `canChangeFiles`, and `reviewable` metadata. Keep these definitions in code and behavior contracts in Markdown; a user-configurable role system is outside this change.

| Role | Supported backends | Can change files | Eligible for change review |
| --- | --- | --- | --- |
| `plan` | Claude, Pi | yes | no |
| `implement` | Claude, Pi | yes | yes |
| `ask` | Claude, Pi | no | no |
| `ultracode` | Claude | yes | yes |
| `security` | Pi | yes | yes |

The existing plan role retains its file-changing classification. Backend-specific bindings supply the concrete tools, model defaults, and effort settings. Reject unsupported role/backend combinations before starting a process. For a new run without an explicit backend, select the sole supported backend when there is one: security selects Pi and ultracode selects Claude. Roles supported by both retain Claude as the default. An explicit incompatible backend fails instead of being replaced.

The `security` role can investigate, write reproductions and tests, implement fixes, and run verification within the task's scope. Give it the Pi coding tools and `contracts/security.md`, with a report covering findings, evidence, changed files, verification, and unresolved issues. Its Pi binding selects the user's configured DeepSeek provider/model id. Other roles can select entirely different providers and models through the same Pi backend.

Security work follows the requested outcome. An investigation task produces findings and may write reproductions or tests to verify them; it does not automatically repair application code. A task requesting investigation and fixes also authorizes remediation within that scope. Keep this distinction in the contract and task brief rather than adding another mode parameter. The role occupies the file-changing slot in either case. When the intended outcome is ambiguous, use the existing question mechanism before expanding into remediation.

Use role capabilities for scheduling, changed-file snapshots, review eligibility, and UI behavior instead of checks such as `role !== "ask"` or a hard-coded implement/ultracode pair. A running or waiting security child blocks every other file-changing child across both backends; ask children can still coexist. Apply the same questions, continuation, cancellation, background, and history behavior as other coding roles.

## Public interface

- Add `fusion` and `fusion_control` as the primary tools. Keep `/fusion` as the user command.
- `fusion` retains the current task, context, role, continue, fresh, background, mode, model, and effort parameters, and adds optional `backend: "claude" | "pi"`. New calls infer a role's sole supported backend, or default to Claude when both are supported. Continuations inherit their recorded backend.
- Pi model values use `provider/model-id`, and selection is strict: the configured provider and model id must appear, exactly, in the child's available models, which is the list the RPC `set_model` command itself checks. Measured in the lifecycle spike: a typo in the model id, a wrong-case id, a glob-shaped id that matches the model it was derived from, and a provider that does not exist were each refused with `Model not found`, and none of them reached the provider. Never resolve a Pi model by pattern, and never fall back to another provider or model; fail clearly when the model or its credentials are unavailable.
- Check the requested thinking level against the child's available levels, then read the selection back and compare provider, model id and level against what was asked for, before any model work. Three source findings in 0.85.1 make the read-back necessary: the `--model` argument matches a model id or name by substring, and a configured model scope matches it as a glob; when a pattern names nothing, Pi synthesizes a model with the requested id from another model of the same provider, with a warning only, so the synthesized entry carries that other model's prices and context window; and setting a thinking level the model does not offer clamps it while RPC still answers success. Every one of those loose resolutions, the substring match, the glob and the synthesis, lives in Pi's own resolver rather than the RPC one, which resolves nothing: the measured refusal of a glob-shaped id shows a model named by pattern failing instead of drifting to a neighbour. The clamp is measured: an unsupported level answered success and read back as the model's highest supported one, and it never appeared in the session's persisted thinking levels. Two more measured details belong in the same sequence. Select the model before the effort: `set_model` recomputes a thinking level for the new model and applies it unconditionally, so it resets a level chosen earlier to the settings default. And any model entry a role selects needs a real context window, because pi-ai clamps a request's output budget to the window minus its own safety margin and floors it at one token: measured at a 4000-token window, the outgoing request asked for a single output token, so a provider that honours the limit truncates anything longer, and automatic compaction then fails outright, because Pi refuses a length-stopped summary as incomplete (source). The spike's fixture ignores `max_tokens`, so what a live provider returns for such a request is untested.
- Each role's backend binding owns its model and effort defaults. For Pi, an explicit call override wins, followed by the recorded selection on continuation, followed by the role's defaults for a new run. There is no shared Pi model default. Preserve existing Claude model-selection behavior for compatibility.
- Keep `claude` as a wrapper selecting the Claude backend, with its existing parameter schema. Reject continuation of a Pi handle through this wrapper. Keep `claude_control` as a compatibility alias of the shared control tool; handles identify the backend.
- Host routing guidance uses the new tools. Existing integrations can continue using the old names.
- Continuing a handle inherits its backend and role. An explicit conflicting backend or role fails before launching a child. Persist the resolved Pi model and effort so continuation after a host restart does not silently select another model.
- Track the implicit latest plan separately per backend. A Pi plan must never silently continue a Claude plan. Handoffs stay on the originating backend.
- Validate role, tools, and effort against the selected backend. Pi 0.85.1 defines the thinking levels `off`, `minimal`, `low`, `medium`, `high`, `xhigh` and `max` (source), and which of them a model offers is model-dependent, measured for the spike's fixture model as `off`, `minimal`, `low`, `medium` and `high` through `get_available_thinking_levels`, so the generic tool's schema accepts the Pi levels, `off` and `minimal` included, alongside the Claude tiers, and accepts a model value per backend binding. Validate the value against the selected backend, role and model instead of translating a Claude effort setting into a level the model does not offer. The `claude` tool keeps its present schema, tiers and model parameter unchanged.

Example, using the model configured for the security role:

```json
{"role":"security","task":"Inspect this project's authentication flow, reproduce confirmed issues, and implement fixes."}
```

## Execution architecture

Extract a small backend interface from `extensions/fusion.ts`. Keep the shared lifecycle in Fusion: handle allocation, scheduling, questions, notifications, reviews, snapshots, history, budgets, and rendering. Backend modules own launch options, protocol translation, session operations, and backend-specific errors.

Suggested files:

- `extensions/backends/types.ts`: backend identity, session references, capabilities, normalized progress and completion types. **Done in step 2**, as far as the Claude backend needs it: the run record, its events, the question callback, the steer queue, the run request and a `Backend` with a name, a steer queue and a run. It names no SDK, and a backend's role and session shapes stay its own, through the generic parameters, rather than being promoted to a shared contract; role capabilities and tagged records are still step 3's.
- `extensions/backends/claude.ts`: existing SDK options, questions bridge, and stream handling, initially moved without behavior changes. **Done in step 2**: the Claude role and session shapes, the executable override, the SDK user-message queue, the `ask_orchestrator` server and the `AskUserQuestion` hook, the stream loop with its accounting, context and workflow handling, and `claudeBackend`, which is what `fusion.ts` runs a child through. `fusion.ts` imports no SDK and keeps its earlier exports as re-exports.
- `extensions/backends/pi.ts`: RPC transport, model validation, events, usage, questions, and session control.
- `extensions/backends/pi-child.ts`: explicitly loaded Pi extension exposing `ask_orchestrator` and internal session-navigation commands.
- `extensions/backends/pi-bootstrap.mjs`: the child's entry module, which builds the runtime from the package's public exports and serves RPC mode. Plain ESM, because node runs it directly rather than through Pi's TypeScript loader.
- `extensions/process-tree.ts`: shared process launch and descendant termination, preserving current cancellation behavior. **Done in step 2**, with its own launch and process shapes so no SDK type reaches it; the Claude backend hands it the SDK's spawn options.

Run the child as a separate process: node runs the bootstrap entry module, which imports the installed `@earendil-works/pi-coding-agent` package and builds the runtime from its public exports, then serves the real RPC mode on the child's stdio. The stock CLI main is not the entry point. The configuration-write spike measured this bootstrap on the repository's Pi 0.85.1, as its case C: it served the whole RPC phase sequence, settled a prompt against a local model fixture, and left both the fake user profile and the disposable project byte-identical across startup, the four persisting RPC setters, that prompt and exit. The same spike measured what the stock CLI does instead: it rewrites the user's `settings.json` from `set_steering_mode`, `set_follow_up_mode`, `set_auto_compaction` and `set_auto_retry`, renames the project's `.pi/commands` during startup even when given a private agent directory and an untrusted project, and creates `models-store.json` beside the models file it reads.

Fusion owns the child's configuration surfaces, which is what makes that measurement hold, not the entry point on its own: settings through `SettingsManager.inMemory`, so the four setters have no file to write; the model catalog cache through `ModelRuntime.create`'s `modelsStorePath`, pointed inside a Fusion-owned child directory, because that store's file backend creates its file before taking its lock (source) and its default sits beside the user's `models.json`; session storage through the directory the bootstrap hands `SessionManager.create`; and extensions, skills, prompt templates and themes through the resource loader's constructor options, with discovery off, rather than CLI flags. Whether that child directory is per host session, per role or per run, and when Fusion recreates it, is a pending decision; the catalog cache and the session storage accumulate in it.

The bootstrap also drops what the CLI did on the way in, and each of those is now Fusion's to decide. It adds none of Pi's built-in extensions (measured: the built-in `llama` command was in every CLI case of the spike and absent in case C), runs no startup migrations (measured, and that is the point), and resolves no model for the child, which the strict selection above replaces. Whether a role's binding passes any built-in extension, and which, is a pending decision. Project trust is a decision too, but not an unmeasured one: the bootstrap's child trusts the project unless Fusion says otherwise. Measured in case C, the child's bridge reported `projectTrusted: true`; source in 0.85.1, `SettingsManager.inMemory` defaults `projectTrusted` to true, while the CLI private-directory cases reported false, because their own settings set `defaultProjectTrust: "never"`. That value gates project settings and project-scoped resources, so which one each role's binding declares is the pending decision.

The API floor is demonstrated on 0.85.1 and nowhere else. The bootstrap uses six public constructors, `SettingsManager.inMemory`, `ModelRuntime.create`, `SessionManager.create`, `createAgentSessionServices`, `createAgentSessionFromServices` and `createAgentSessionRuntime`, plus `runRpcMode` (measured on 0.85.1). The wildcard peer dependency pins none of them, so check the exports and the protocol capabilities at child startup and refuse with an actionable error that names the version, rather than assume another Pi version behaves the same. The spike's one comparison run against a globally installed 0.87.1 covered the stock CLI only, so it says nothing about the bootstrap there. One more measured detail the bootstrap has to respect: the package publishes no `require` condition, so its entry resolves as ESM only.

Use LF-delimited JSON framing, correlated command ids, bounded diagnostics, and explicit handling of malformed output and unexpected exit. A successful prompt response acknowledges acceptance; it does not mean the task succeeded, and RPC emits it from a preflight callback before the turn runs (source, and measured in the lifecycle spike: a prompt whose bridge command failed still answered success). Failures also arrive as events of their own, `extension_error` among them, so read the event stream as first class rather than only the command replies. Finish only after `agent_settled`, inspect the final outcome, collect usage and checkpoint, then shut down the child. Measured why `agent_end` is not the place to stop: a retried call emitted `agent_end` with `willRetry` before `auto_retry_start`, an automatic compaction emitted `compaction_start` and `compaction_end` after an `agent_end`, an overflow recovery ran a summary and a second attempt inside the same call, and a queued follow-up ran its own turn, with exactly one `agent_settled` for the pair in each case, and nothing after it in a measured quiet window for the retry, the overflow recovery and the queued turn. Handle retries, compaction, and queued steering without prematurely completing the run.

Retain process-tree termination for cancellation and host shutdown, and record descendant pids to terminate per pid, not only per group. All three are measured: an abort with a steer and a follow-up still queued was followed by one further provider request carrying both, so `clear_queue` has to precede abort; a `setsid` grandchild of a Bash call outlived both an abort and a clean stdin shutdown, because Pi's cleanup is a process-group `SIGKILL` with a per-pid fallback and its graceful path is the same group kill (source), while an explicit per-pid signal from the harness did reach it; and a cancelled question is released inside the child by the forwarded abort signal with nothing written back for its request id, so the host must treat its own cancellation as that question's answer. Reject pending requests and release pending questions when the child exits or is cancelled.

## Child configuration and questions

Each role's Pi binding declares explicit extension and skill lists, which the bootstrap passes as constructor options with discovery off, so nothing is loaded from global settings, the project or packages; those lists plus the Fusion child bridge are all the child gets. Empty lists mean no optional extensions or skills. Provider extensions a role needs are listed the same way. Measured in the spike: the explicit lists kept a seeded user extension, project extension, skill, prompt template and package extension out of the child's command list, and an explicitly listed provider extension reached the child's available models on the bootstrap path, with no provider entry copied into any models file. Validate configured resources before starting work and report missing resources without silently loading alternatives. One caveat carries over from the spike: package resolution still runs with discovery off, and `PI_OFFLINE` is what stops a configured package from being installed at child startup (source, not executed there); whether Fusion sets it for children, given that it also stops catalog refreshes, is a pending decision.

Credentials and model configuration stay the user's, read in place and never created. `ModelRuntime.create`'s `modelsPath` reads the user's `models.json` where it is, and its `authPath` reads an existing `auth.json` where it is; measured, that left both files byte-identical through a whole run. What must not happen is opening a user auth path that does not exist: measured, a child pointed at a missing user `auth.json` created it as an empty file with mode 600, and the user's own next Pi startup then skipped its legacy auth migration, because that migration returns early once `auth.json` exists (source). The same file backend sits behind `ModelRuntime.create`'s `authPath` (source; untested for that entry point). So the rule is narrow: read a user auth file only when it already exists, and otherwise give the child an explicit credential mechanism, either `ModelRuntime.create`'s credentials store or a Fusion-owned auth path inside the child's own directory, or fail with an actionable error. Never create a file in the user's profile. `AuthStorage` is not a public export in 0.85.1, and its deep import is not exported either (both measured), so credential handling goes through `ModelRuntime.create`'s options rather than a private module. Any design that resolves a key and hands it to the child through its environment or argv also puts a copy in Fusion's memory and in the child's process table (measured for the CLI's key flag: the value stayed off disk and stood in argv for the run). That copy is where it stops: a resolved credential is never written into a Fusion record, not the host session entry, not the history mirror, not the dashboard.

"The child writes nothing outside its own directory" is not a claim this proposal makes. Neither is the blanket promise these classes replace, that the child would "not edit the user's existing Pi configuration": that sentence is the one the configuration-write spike set out to test, and this is what survived it. Three different things are in play, and only the first is about the bootstrap:

- The child's own startup and settings commands. Measured: with the surfaces above owned by Fusion, they wrote nothing in the user's profile and nothing in the project, and the only watched write was the catalog cache in the child's own directory. The child also writes its session storage in the directory the bootstrap hands `SessionManager.create`, which the configuration-write spike did not watch; the lifecycle spike measured that half instead, creating, reopening and forking durable sessions inside Fusion-owned session directories, one per case inside its temp root and deleted afterwards. What stays open is not whether the writes land there but the product policy for that storage's lifetime and location, per host session, per role or per run, which is the pending decision above.
- An OAuth credential in an auth file that Fusion and the user intentionally share. Source, not tested, and with no fixture here: an expiring token is refreshed inside the credential store's modify call, which writes the rotated credential back into the user's file. That is the store working as designed, and it applies to any path that reads the user's `auth.json`. Whether Fusion should share a credential that can rotate, require the child to hold its own, or refuse the case is a pending decision; no policy for it is approved, and this proposal deliberately does not propose a configurable one or an implementation.
- Whatever the child's tools, extensions, a `!command` credential helper in `models.json`, or Bash choose to write. Nothing here sandboxes that, on any of the options the spike compared.

Prevent the Fusion host extension from registering recursively in a child, including indirect package loading, using a child marker and an early guard in the host extension. Reject an explicit attempt to include the Fusion host extension in a role's resources. The child bridge is separate and does not expose tools for starting Fusion children. Contracts also prohibit launching nested Fusion sessions; the resource controls and registration guard are not a sandbox against arbitrary Bash execution.

Disable automatic prompt-template discovery as well; configurable child prompt templates are outside the initial scope. The project's instructions stay: measured for `AGENTS.md`, the project's context file reached the child's system prompt in every case of the spike, trusted project or not, while the user-level one reached only the child whose agent directory was the user's. Source: Pi tries `AGENTS.override.md`, `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md` and `CLAUDE.MD` in each directory and takes the first that exists, so a project holding both file names contributes only its `AGENTS.md` and never its `CLAUDE.md`. A Fusion-owned child directory therefore keeps the project's instructions and drops the user's global ones, which is what this plan wants. The rest of the system prompt is a pending decision rather than an assumption: what else the CLI contributed that the bootstrap does not, and which built-in extensions a role passes, each need a measurement before the adapter depends on it, while the trust value a binding declares is a decision against the default above rather than a measurement. Reviews load the ask/review role's explicitly selected resources, not the source coding role's tools or skills; any provider extension needed for the selected reviewer model must be available in that configuration.

The child bridge registers `ask_orchestrator`, implemented through a blocking RPC UI input request. The parent maps its request id to the existing question queue and replies through `extension_ui_response`. The child half is measured in the lifecycle spike: the open request held the child with no provider request in a measured window, the answer arrived as the tool result correlated to the tool call id, a second reply for the same request id was silently dropped with no second tool result and no further provider request (source: the pending request is deleted on first use), two questions in a row each held the child in turn, and a steer queued while a question waited was delivered after the tool result as an ordinary user message at the start of the next turn. The run's tool list has to name the question tool, or the session's allowed tool names filter the bridge's registration out. Reuse exactly-once answer arbitration between host and user, foreground-to-background transition, and cancellation behavior; which side supplies an answer is Fusion's arbitration and the spike does not model it. Other supported extension dialogs must receive a defined response or an explicit error, never silently hang.

Contracts need backend-neutral language: use host/child vocabulary, remove the fixed three-model framing, and describe tools by capability or provide backend-specific instructions. Pi does not inherently provide Claude's `WebSearch` and `WebFetch`; advertise only tools actually configured. The existing `ask` role remains non-mutating by contract, including Bash. This is not a filesystem sandbox.

## Durable sessions and branching

Use backend-tagged session references. Claude keeps its session id and assistant checkpoint. Pi records its session file, session id, and durable entry checkpoint after the successful call has settled. That checkpoint is the leaf at settle, whatever kind of entry it is, and the lifecycle spike measured why the weaker rule is wrong: an automatic compaction appends a `compaction` entry as a child of the last assistant message and leaves it as the leaf, so a checkpoint taken as the last assistant message is that entry's ancestor, and restoring it drops the compaction off the branch and rebuilds the whole pre-compaction history. Missing backend fields in old records mean Claude.

The child's session navigation must restore the recorded checkpoint before sending another prompt, on every start. The stock RPC `fork` command branches from a user message and is insufficient for Fusion's completed-call checkpoint semantics. The bridge's command-context `navigateTree` and `fork` with position `at`, without summary generation, are now measured rather than merely available: the lifecycle spike restored recorded checkpoints, older checkpoints and post-compaction checkpoints with `navigateTree`, and measured that a `fork` at an exact entry contains precisely that entry's ancestry and that the two transcripts then stay byte-isolated from each other. Three measured details the adapter has to respect. The leaf is not persisted, so a reopened session sits at the file's last line, which after an abandoned call is that failure's own entry; restoration is mandatory and its postcondition is the proof. `SessionManager.open` on a path that does not exist does not fail, it binds a brand new session id to that path, and a checkpoint id absent from an existing file makes `navigateTree` throw inside a live session, so the child has to preflight the file and the checkpoint id and refuse before a session exists. And `fork` ignores a supplied session id: `createBranchedSession` generates its own (source), measured by passing one in and reading back a different one, so for Pi the record has to carry the id the child reports and a fork has no identity until the fork call returns. That is a change to `nextSession`'s contract, which today allocates a fork id up front, and it is the one record rule that cannot transfer unchanged.

Verify every navigation and fork by postcondition, never by a prompt going through. Read the session id and session file back from the child's state, the leaf id and branch shape from its tree, and the restored context from its entries, then require the recorded checkpoint to be the leaf and the context to be the one the record names. A prompt acknowledgement proves nothing about it: RPC reports a prompt as successful from a preflight callback, and a bridge command that failed surfaces as its own `extension_error` event. Measured in the lifecycle spike: an absent navigation target answered `Entry ... not found` and an absent fork target `Invalid entry ID for forking`, each as an `extension_error` carrying `extensionPath command:...`, while the prompt that carried them answered success, and the session id, session file, leaf and entry count were all unchanged. Treat a postcondition mismatch as a failed call. A refused operation therefore has three shapes to tell apart, not one: a thrown command reported as an `extension_error`, a postcondition that disagrees with the record, and a cancellation that is an ordinary `{ cancelled: true }` result with no error at all.

Required semantics:

- Normal continuation reads exactly the recorded context, including after a host restart.
- Host `/tree` restores the older child checkpoint and excludes later child turns. Measured on the child side: restoring an earlier checkpoint sent exactly that turn's context, the later turn appeared in neither the prompt nor the answer, and the durable file kept both continuations as sibling branches of the restored entry. The host's own record selection and its refusal to move the tree while a run is unfinished have no Pi child in them and stay unexercised.
- A forked host creates a separate child session from the recorded checkpoint on first use. Neither host subsequently writes the other's child transcript. Measured for the child half: the fork's entries were exactly the checkpoint's ancestry, entry for entry, its header pointed back at the parent session file, and each file's bytes were unchanged while the other took a turn, with neither payload carrying the other's prompt.
- Accepting a navigation or a fork needs two answers, in this order, before any task prompt: a non-cancelled operation result, and then verified postconditions. Measured in the lifecycle spike: an extension that answers `{ cancel: true }` to `session_before_tree` or `session_before_fork` makes the bridge's `navigateTree` and `fork` return `{ cancelled: true }` as an ordinary result, with the prompt that carried the command still answering success and no `extension_error` anywhere, and a cancelled fork leaves the child on the source session id and file with no branched transcript created, so a guard that only watches for errors walks straight past it. Nor is a postcondition that happens to hold permission to ignore `cancelled: true`: measured, a navigation to the entry that is already the leaf never reaches the hook at all and answers `{ cancelled: false }`, so "the leaf is the target" says nothing about whether an operation ran. A cancelled operation records nothing and submits nothing. Cancellation before a fork exists leaves the prior durable reference authoritative, which is the same shape as a failed resume below, and it does not touch the rule for a failure after a new fork identity exists.
- A call that failed after it resumed a recorded session records nothing, so the last successful checkpoint stays authoritative and the next call continues from it.
- A fork that failed after the child reported its new session records that session id together with the checkpoint it forked at, so the fork is not repeated and the context it branched from is what the next call gets.
- A new run that failed before any session exists records its handle alone, so the handle is never given out again and the next call to it starts a new session. Context fill is recorded only for a call that succeeded. Measured for Pi: a first call that reaches a provider error is not that case. The child had already reported a session id and the session file existed on disk, holding the failed prompt and an assistant entry with `stopReason "error"`, so the handle-only record applies only to a failure before the child reported a session at all.
- Missing sessions or checkpoints cause an actionable error, never continuation from whatever context happens to remain. The child's preflight above is what makes that fail closed rather than silent. A record with no checkpoint is the one case the Claude backend takes a whole session: it resumes the whole session in the host that recorded it, and forks the whole session in a forked host, because `nextSession` carries a position only when the record has a checkpoint (source; the deterministic tests cover the checkpoint-less resume and the checkpointed fork, not the checkpoint-less fork). What either should mean for a Pi child is now a decision against a measurement rather than a guess: measured, reopening a failed new call's session whole and prompting again replayed the failed prompt, and the error entry stayed in the child's context while this provider adapter dropped it from the request, leaving two consecutive user messages. So a whole-session resume is not the neutral fallback for Pi that it is for Claude. Fail the call, or define a narrower recovery; this decision is still pending, and the plan does not pick one here.
- Keep `/tree` refused until every unfinished run has recorded its entry and delivered its result, across both backends.

Use supported Pi session APIs rather than hand-editing JSONL transcripts. Add migration tests for existing host entries and history files. Child transcripts remain durable independently of the optional Fusion history mirror.

## Shared behavior and visibility

- Enforce the single active file-changing run rule across both backends using role capabilities, including `security`; `ask` runs may coexist.
- Add backend and resolved provider/model to cards, status, dashboard, history, and resume instructions. A Pi run must never suggest `claude --resume`.
- Keep accounting per call, from a baseline rather than from a total. Pi's session statistics sum the usage of every entry in the session, retry and compaction entries included: source, the summation loops over every entry the session holds rather than the current branch; measured, two calls of 128 tokens each read back as a session total of 256, and a call whose turn triggered an automatic compaction reported a delta covering both the turn and the summary request. Take the baseline after a restore or fork and before each task prompt and report the difference; a continued run that reads the total counts every earlier call again. The ledger's existing rule still holds: each call reports a running total that replaces the one before it, never a delta.
- Treat all-zero prices as an unavailable estimate unless the price provenance is known. Pi starts each usage record's cost at zero and fills it from the selected model's price table (source), so a model with no prices, or a synthesized id carrying another model's table, yields a number that looks like a cost and is not one. Say the estimate is unavailable instead of reporting zero dollars, and keep saying which part of a budget estimate is incomplete.
- Use Pi's reported context usage and window for context caps and handoffs instead of Claude defaults, and treat an unknown context as unknown. Measured: immediately after an automatic compaction the reported usage was null tokens and a null share beside a known window, and it read back null again across a child restart and a checkpoint restore. Two limits on the same value are source rather than measured, because the spike configured no model without a context window and read no usage after the continuation's own turn: Pi reports no context usage at all when the selected model has no context window, and after a compaction the nulls last until an assistant turn answers on the compacted context. A missing value must never be read as the last known one and must never start a handoff; wait for the next model turn, and say the context is unknown where a share is shown.
- Preserve current Claude review defaults for existing roles. Security changes use a fresh Pi `ask` run with `mode: "review"`, a read-only review contract, and the security run's resolved model, including any explicit model override. Include successful security runs with changed files in the existing opt-in automatic review behavior. Manual `/fusion review` and automatic review use the same reviewer-selection policy.
- Preserve dashboard DOM and CSS restrictions.

Proposed new configuration: role-specific `PI_FUSION_PI_<ROLE>_MODEL` and `PI_FUSION_PI_<ROLE>_EFFORT` values, and explicit extension and skill lists in each role's Pi binding. For example, `PI_FUSION_PI_SECURITY_MODEL` configures the security role's DeepSeek provider/model id. These configure role bindings, not provider behavior in the backend. Existing Claude variables keep their meaning. Require a model from the call, continued run, or role configuration; do not guess the user's DeepSeek model id or use Pi's last interactive model selection.

`PI_FUSION_PI_BIN` is not part of this proposal. It was an executable override for a CLI entry point the child no longer uses, and redefining it as an import path, a package specifier or a test hook is a design that does not exist yet. The default is to import the installed supported package from the bootstrap entry module. Any override added later has to keep the isolation the spike measured, Fusion-owned settings, catalog cache, session directory and resource lists, and must not reach the stock CLI main. Until that design is written, the deterministic tests still need a way to name a child process of their own, and this document says nothing about how it is spelled.

Keep reviewer selection separate from execution, as a per-source-role policy resolving a reviewer backend, model, and supported effort settings. Initially, security selects Pi and inherits the source run's resolved model; existing roles retain their current reviewer defaults. A review is a new run with its own context and the review contract, never a continuation of the coding child. Inheriting the model does not inherit coding tools or permissions. Record the resolved reviewer backend/model on the review run.

Plan the internal policy to accept an explicit reviewer model later, but defer new reviewer-model configuration variables, command options, and UI controls. A future override should require only selection/configuration changes, not another execution path or changes to review prompts and lifecycle. Existing explicit `fusion` calls with `role: "ask"`, `mode: "review"`, and a model remain available.

## Implementation sequence

1. Spike the two boundaries before committing to the adapter shape. **Complete.** [docs/pi-config-write-spike.md](pi-config-write-spike.md) compared the ways of starting a child, picked the bootstrap above and measured what it writes. [docs/pi-session-lifecycle-spike.md](pi-session-lifecycle-spike.md) measured the session lifecycle against installed Pi 0.85.1 with a deterministic loopback model fixture, each claim checked by postcondition rather than by a prompt going through: checkpoint restoration after a child restart, an older checkpoint and a post-compaction checkpoint, an exact-position fork and its isolation, the four failure shapes, a navigation and a fork an extension hook cancelled, a question that holds its child until one answer arrives, cancellation including a descendant that leaves the killed process group, settled completion after retry and automatic compaction, the usage baseline, and strict model and thinking-level selection. Ten cases cover its eight acceptance rows and all ten are measured passes. What that spike could not measure is named there and carried forward here: every host record decision it exercised is a simulation of `nextSession` and `recordRun` rather than Fusion code, the `/tree` refusal has no host to exercise it, and a loopback fixture says nothing about a live provider, which is what step 6's smoke run is for. The two protocol gaps it found are resolved in this document ahead of the adapter: the checkpoint is the leaf at settle, and a fork's session id comes from the child. The two questions it turned into decisions rather than answers, what a record with no checkpoint means for Pi and whether a branch ending in an error entry may be resumed at all, are named as pending above and have to be settled in step 3, where records are written, not later.
2. Extract the backend boundary and process-tree helper while keeping all Claude behavior and tests passing. **Complete.** `extensions/backends/types.ts`, `extensions/backends/claude.ts` and `extensions/process-tree.ts` hold what moved; `fusion.ts` kept handles, role routing, questions, scheduling, records, reviews, snapshots, history, the ledger and rendering, and routes execution through `claudeBackend`. `test/backends.test.ts` asserts the split: no backend SDK in the host, the boundary types or the helper, no import at all in the boundary types, only node's own in the helper, and no path from the backend back to the extension. The 325 tests that covered the Claude behavior are unchanged and pass.
3. Add tagged records, generic tools, compatibility wrappers, explicit role capabilities and backend bindings, backend-aware routing, and per-backend plan selection. Keep the legacy Claude schema limited to its existing roles.

   Acceptance gate for step 3, to be settled before the first tagged record is written rather than after it:

   - **Recovery for a first Pi call that failed with an identity but no checkpoint.** Measured: such a call has already reported a session id and left its session file on disk, holding the failed prompt and an assistant entry with `stopReason "error"`, so the record it produces names a session file and a session id and carries no successful checkpoint. Reopening that session whole replays the failed prompt and leaves two consecutive user messages, so the Claude backend's whole-session resume is not the neutral fallback here. Decide that record's recovery and write it in this document: fail the next call for the handle with an actionable error, or define a narrower recovery and say what it restores. The other end is already settled and stays as it is: a failure before the child reported any session records the handle alone, and the next call for that handle starts a new session. This is the first of the two questions the lifecycle spike named for this step.
   - **How the child's reported session identity reaches the durable record.** Who allocates a fork's id is settled and not reopened: Pi does, and the record carries what the child reports. What step 3 owes is the path, because `nextSession` allocates a fork id up front today and a Pi fork has no identity until the fork call returns. Define the write point instead of adding a field: the record for a Pi run is written from what the child answered, after it answered. A Pi record carries a session-file reference, the session id and the durable checkpoint, which the semantics above already require, and no speculative extra fork-id field for an identity the host guessed.
   - **The two settled failure semantics are preserved by whatever the recovery decision turns out to be.** A call that failed after resuming a recorded session still records nothing and leaves the last successful checkpoint authoritative. A fork that failed after the child reported its new session still records that session id together with the checkpoint it forked at, so the fork is not repeated. A cancelled operation before a fork exists still records nothing, which is the rule the required semantics above state.
   - **Whether a branch that ends in an error entry may be resumed at all**, which is the second question the spike named for this step, and is separate from the recovery decision above because the payload hazard it rests on is specific to one provider adapter.
4. Implement the bootstrap entry module, the Pi transport and the bridge, then wire continuation, questions, steering, cancellation, and background reports into the shared lifecycle.

   Acceptance gate for step 4, to be settled before the Pi adapter is wired into the shared lifecycle:

   - **A descendant ownership strategy, written down before any code changes for it.** Say which processes a run owns, how they are discovered while their ancestry is still observable rather than after the root has gone, and what the resulting guarantee is. The guarantee has to be bounded and platform-qualified: polling a process table cannot promise to have seen every descendant that existed for a moment, and this document must not claim it does. `extensions/process-tree.ts` as it stands does not meet that gate, and none of this is a step 2 regression: the helper it moved already scanned for descendants only while sending a signal, already re-signalled its remembered pids without checking that a pid is still the process it recorded, and already returned from `exited()` as soon as the child closed, without a later sweep. Step 4 decides the strategy; do not change the helper before it is decided.
   - **Identity-safe late signals.** A pid that has been reaped can be reused, so a remembered pid needs an identity to go with it, such as its start time on Linux, before a later `SIGTERM` or `SIGKILL` is aimed at it. Say what that identity is on each platform the guarantee claims, and treat "not ours" as the safe answer where it cannot be established.
   - **Cleanup after a normal root exit, not only after an abort.** Measured in the lifecycle spike on both paths: a `setsid` grandchild of a Bash call survived Pi's abort *and* survived closing the child's stdin for a clean exit with code 0, because Pi's own cleanup is a process-group kill. A descendant that escaped its group, or that was re-parented when its own parent died, has to be reaped by whatever owns the run, on the ordinary exit path as well as the cancelled one.
   - **Shutdown ordering for a Pi child.** `clear_queue` before `abort`, measured: an abort with a steer and a follow-up still queued was followed by one further provider request carrying both. Then settle or reject every pending request and release every pending question, because a cancelled dialog is never answered back to the host and the host's own cancellation is that question's answer. Then reap the descendants the run owns.
   - **What stays pending here rather than being assumed.** The OAuth-refresh policy for a credential file Fusion and the user share; the explicit configuration the child inherits, including the project trust value a binding declares and which built-in extensions, if any, a role passes; preventing a configured package from being installed at child startup, which is what `PI_OFFLINE` does and which also stops catalog refreshes; and the location and lifetime of the child directory and the session storage inside it, per host session, per role or per run. Each is a decision this step has to make explicitly. Two neighbouring decisions are already made and are not reopened by it: a role declares explicit extension and skill lists with discovery off, and a fork's id comes from the child.
5. Add the security contract and Pi binding; complete usage, context caps, capability-based reviews, history, and dashboard integration. Update contracts and documentation alongside each behavior change.
6. Run the full deterministic suite and typecheck, then perform a user-configured DeepSeek smoke run as an explicit live validation step.

## Acceptance and verification

Cover success, streamed tools, two questions, competing answers, steering, cancellation with a Bash descendant, protocol errors, provider errors, retry/compaction before settled completion, and premature process exit. Descendant termination has to be tested through the production discovery and cleanup path, never by handing the implementation the pids a fixture already knows. A fixture pid is an assertion oracle, and an emergency-cleanup oracle for the test's own `finally`; the set of processes to signal has to be the one the code under test found for itself. `test/child.test.ts`'s "aborting kills a detached grandchild that ignores SIGTERM" is already that shape for a Claude abort: the fake starts a real detached grandchild, reports its pid through a file, and the assertion is that the production path killed it.
