## Outcome

The host can run a child through either Claude Code or Pi, with the same handles, background work, questions, controls, dashboard, and durable continuation. Pi uses the user's working provider configuration, including DeepSeek; Fusion does not implement a provider API client.

Backend and role are independent. A backend chooses the execution harness; a role chooses the task contract, available tools, and model in its backend binding. The Pi backend is provider-neutral and contains no DeepSeek-specific defaults or routing. Backend selection follows the requested backend, the continued run, or the role's supported backends; a child's refusal never triggers automatic backend switching.

## Role capabilities and backend support

Define roles separately from backend implementations, with explicit supported backends, required tool capabilities, `canChangeFiles`, and `reviewable` metadata. Keep these definitions in code and behavior contracts in Markdown; a user-configurable role system is outside this change.

| Role | Supported backends | Can change files | Eligible for change review |
| --- | --- | --- | --- |
| `plan` | Claude, Pi | yes | no |
| `implement` | Claude, Pi | yes | yes |
| `ask` | Claude, Pi | no | no |
| `ultracode` | Claude | yes | yes |
| `security` | Pi | yes | yes |

The existing plan role retains its file-changing classification. Backend-specific bindings supply the concrete tools, model defaults, and effort settings. Reject unsupported role/backend combinations before starting a process. For a new run without an explicit backend, select the sole supported backend when there is one: security selects Pi and ultracode selects Claude. Roles supported by both retain Claude as the default. An explicit incompatible backend fails instead of being replaced.

The `security` role can investigate, write reproductions and tests, implement fixes, and run verification within the task's scope. Give it the Pi coding tools and `contracts/security.md`, with a report covering findings, evidence, changed files, verification, and unresolved issues. Its Pi binding selects the user's configured DeepSeek provider/model id. Other roles can select entirely different providers and models through the same Pi backend.

Security work follows the requested outcome. An investigation task produces findings and may write reproductions or tests to verify them; it does not automatically repair application code. A task requesting investigation and fixes also authorizes remediation within that scope. Keep this distinction in the contract and task brief rather than adding another mode parameter. The role occupies the file-changing slot in either case. When the intended outcome is ambiguous, use the existing question mechanism before expanding into remediation.

Use role capabilities for scheduling, changed-file snapshots, review eligibility, and UI behavior instead of checks such as `role !== "ask"` or a hard-coded implement/ultracode pair. A running or waiting security child blocks every other file-changing child across both backends; ask children can still coexist. Apply the same questions, continuation, cancellation, background, and history behavior as other coding roles.

## Public interface

- Add `fusion` and `fusion_control` as the primary tools. Keep `/fusion` as the user command.
- `fusion` retains the current task, context, role, continue, fresh, background, mode, model, and effort parameters, and adds optional `backend: "claude" | "pi"`. New calls infer a role's sole supported backend, or default to Claude when both are supported. Continuations inherit their recorded backend.
- Pi model values use `provider/model-id`, and selection is strict: the configured provider and model id must appear, exactly, in the child's available models, which is the list the RPC `set_model` command itself checks. Measured in the lifecycle spike: a typo in the model id, a wrong-case id, a glob-shaped id that matches the model it was derived from, and a provider that does not exist were each refused with `Model not found`, and none of them reached the provider. Never resolve a Pi model by pattern, and never fall back to another provider or model; fail clearly when the model or its credentials are unavailable.
- Check the requested thinking level against the child's available levels, then read the selection back and compare provider, model id and level against what was asked for, before any model work. Three source findings in 0.85.1 make the read-back necessary: the `--model` argument matches a model id or name by substring, and a configured model scope matches it as a glob; when a pattern names nothing, Pi synthesizes a model with the requested id from another model of the same provider, with a warning only, so the synthesized entry carries that other model's prices and context window; and setting a thinking level the model does not offer clamps it while RPC still answers success. Every one of those loose resolutions, the substring match, the glob and the synthesis, lives in Pi's own resolver rather than the RPC one, which resolves nothing: the measured refusal of a glob-shaped id shows a model named by pattern failing instead of drifting to a neighbour. The clamp is measured: an unsupported level answered success and read back as the model's highest supported one, and it never appeared in the session's persisted thinking levels. Two more measured details belong in the same sequence. Select the model before the effort: `set_model` recomputes a thinking level for the new model and applies it unconditionally, so it resets a level chosen earlier to the settings default. And any model entry a role selects needs a real context window, because pi-ai clamps a request's output budget to the window minus its own safety margin and floors it at one token: measured at a 4000-token window, the outgoing request asked for a single output token, so a provider that honours the limit truncates anything longer, and automatic compaction then fails outright, because Pi refuses a length-stopped summary as incomplete (source). The spike's fixture ignores `max_tokens`, so what a live provider returns for such a request is untested.
- Each role's backend binding owns its model and effort defaults. For Pi, an explicit call override wins, followed by the recorded selection on continuation, followed by the role's defaults for a new run. There is no shared Pi model default. Preserve existing Claude model-selection behavior for compatibility.
- Keep `claude` as a wrapper selecting the Claude backend, with its existing parameter schema. Reject continuation of a Pi handle through this wrapper. Keep `claude_control` as a compatibility alias of the shared control tool; handles identify the backend.
- Host routing guidance uses the new tools. Existing integrations can continue using the old names.
- Continuing a handle inherits its backend and role. An explicit conflicting backend or role fails before launching a child. Persist the resolved Pi model and effort so continuation after a host restart does not silently select another model.
- Track the implicit latest plan separately per backend. A Pi plan must never silently continue a Claude plan. Handoffs stay on the originating backend.
- Validate role, tools, and effort against the selected backend. Pi 0.85.1 defines the thinking levels `off`, `minimal`, `low`, `medium`, `high`, `xhigh` and `max` (source), and which of them a model offers is model-dependent, measured for the spike's fixture model as `off`, `minimal`, `low`, `medium` and `high` through `get_available_thinking_levels`, so the generic tool's schema accepts the Pi levels, `off` and `minimal` included, alongside the Claude tiers, and accepts a model value per backend binding. Validate the value against the selected backend, role and model instead of translating a Claude effort setting into a level the model does not offer. The `claude` tool keeps its present schema, tiers and model parameter unchanged.

Example, using the model configured for the security role:

```json
{"role":"security","task":"Inspect this project's authentication flow, reproduce confirmed issues, and implement fixes."}
```

## Execution architecture

Extract a small backend interface from `extensions/fusion.ts`. Keep the shared lifecycle in Fusion: handle allocation, scheduling, questions, notifications, reviews, snapshots, history, budgets, and rendering. Backend modules own launch options, protocol translation, session operations, and backend-specific errors.

Suggested files:

- `extensions/backends/types.ts`: backend identity, session references, capabilities, normalized progress and completion types. **Done in step 2**, as far as the Claude backend needs it: the run record, its events, the question callback, the steer queue, the run request and a `Backend` with a name, a steer queue and a run. It names no SDK, and a backend's role and session shapes stay its own, through the generic parameters, rather than being promoted to a shared contract; role capabilities and tagged records are still step 3's.
- `extensions/backends/claude.ts`: existing SDK options, questions bridge, and stream handling, initially moved without behavior changes. **Done in step 2**: the Claude role and session shapes, the executable override, the SDK user-message queue, the `ask_orchestrator` server and the `AskUserQuestion` hook, the stream loop with its accounting, context and workflow handling, and `claudeBackend`, which is what `fusion.ts` runs a child through. `fusion.ts` imports no SDK and keeps its earlier exports as re-exports.
- `extensions/backends/pi.ts`: RPC transport, model validation, events, usage, questions, and session control.
- `extensions/backends/pi-child.ts`: explicitly loaded Pi extension exposing `ask_orchestrator` and internal session-navigation commands.
- `extensions/backends/pi-bootstrap.mjs`: the child's entry module, which builds the runtime from the package's public exports and serves RPC mode. Plain ESM, because node runs it directly rather than through Pi's TypeScript loader.
- `extensions/process-tree.ts`: shared process launch and descendant termination, preserving current cancellation behavior. **Done in step 2**, with its own launch and process shapes so no SDK type reaches it; the Claude backend hands it the SDK's spawn options.

Run the child as a separate process: node runs the bootstrap entry module, which imports the installed `@earendil-works/pi-coding-agent` package and builds the runtime from its public exports, then serves the real RPC mode on the child's stdio. The stock CLI main is not the entry point. The configuration-write spike measured this bootstrap on the repository's Pi 0.85.1, as its case C: it served the whole RPC phase sequence, settled a prompt against a local model fixture, and left both the fake user profile and the disposable project byte-identical across startup, the four persisting RPC setters, that prompt and exit. The same spike measured what the stock CLI does instead: it rewrites the user's `settings.json` from `set_steering_mode`, `set_follow_up_mode`, `set_auto_compaction` and `set_auto_retry`, renames the project's `.pi/commands` during startup even when given a private agent directory and an untrusted project, and creates `models-store.json` beside the models file it reads.

Fusion owns the child's configuration surfaces, which is what makes that measurement hold, not the entry point on its own: settings through `SettingsManager.inMemory`, so the four setters have no file to write; the model catalog cache through `ModelRuntime.create`'s `modelsStorePath`, pointed inside a Fusion-owned child directory, because that store's file backend creates its file before taking its lock (source) and its default sits beside the user's `models.json`; session storage through the directory the bootstrap hands `SessionManager.create`; and extensions, skills, prompt templates and themes through the resource loader's constructor options, with discovery off, rather than CLI flags. Where that child directory lives and how long it lasts is settled by the storage decision below: one stable child agent directory at `<host-agent-dir>/pi-fusion/children`, reused across Pi invocations, holding the catalog cache and the helper bin, with per-project durable session storage below it and kept apart from those caches. All of it accumulates, and nothing collects it.

Four of the bootstrap's and the storage's refusals are policy rather than mechanics, and all four are implemented and measured against real children by the implementation stage of [docs/pi-config-write-spike.md](pi-config-write-spike.md). **Current format and framing only.** A recorded transcript is opened only when its header version is the one this Pi writes and when every line of it is json and the file ends with a newline: `SessionManager.open` migrates an older format in place, and Pi's own loader appends a missing final newline to the file and skips a line it cannot read, so a run that merely wanted to continue a session would otherwise rewrite the file a later fork reads or open it with part of it silently dropped. The preflight therefore reads the bytes, checks the framing, and reads the entries through the public `parseSessionEntries`, and it repairs nothing and migrates nothing whatever it finds; it is a conservative gate, not a recovery feature, and which entry a run may navigate to stays the bridge's. Measured: ten broken transcripts — missing, empty, headerless, a malformed line leading and trailing, a stripped final newline, an older and a newer header version, the wrong session id and an unknown checkpoint — each refused a real child at the session stage with exit 78, each leaving the file byte-identical, and none of them reaching the model runtime. **The private models path is absent on purpose.** A user with no `models.json` is given a path inside the call's own directory that nothing creates, because `ModelRuntime.create` given no models file at all falls back to an in-memory catalog store and ignores `modelsStorePath`, which would throw away the persistent store this layout publishes; a path that is simply absent loads as an empty configuration and keeps the shared store. Measured: the per-call `models.json` was never created in any case, the shared store was used, and a stray `models.json` seeded in the stable child agent directory was neither read nor written. **A catalog directory without its store is refused rather than used.** The store's file backend writes `{}` into a missing file before it takes its lock, so a child that decided the file was absent can truncate a store another child has since populated; the whole directory is therefore published by renaming a complete one into place, whoever renames first wins, a publisher that loses removes its own staging directory and uses the winner's, and a directory that is there without its store is a refusal naming what to repair rather than a cold file to create. Measured: a publisher deliberately held inside its staging window lost the rename to an initializer that had already populated the cache, read the winner's bytes unchanged before its own child started, and ran on them without a catalog request of its own; two overlapping children left one catalog directory and lost no provider entry against a single-child control. **A model-configuration error refuses the call, conservatively and without quoting itself.** `getError()` is an aggregate of the configuration error, every provider composition error and the availability-refresh error, with no public way to tell them apart or to attribute one to a provider, so any reported error fails the call — including one about a provider this call never uses — because a call that ran anyway would be running on a configuration the user's own file was silently dropped from. The refusal carries Fusion's own fixed wording and the models path the host passed in, and nothing the SDK produced, because a configuration error's text can quote `models.json` and that file holds credentials. Measured: a malformed models file holding a credential marker refused a real child at the models stage with the fixed wording, and the marker appeared nowhere on stderr. One of the two review notes about this is closed: task 3 rechecks `getError()` after `createAgentSessionServices`, which registers an extension's providers and refreshes the catalog, so an error raised by that work refuses the call in the same fixed wording — before the exact model is looked up and before any resource finding is reported, which the suite covers with a case where a model error and a resource error are both waiting. What remains is task 4's: the auth-stage diagnostic wording is refined with that task's evidence.

The bootstrap also drops what the CLI did on the way in, and each of those is now Fusion's to decide. It adds none of Pi's built-in extensions (measured: the built-in `llama` command was in every CLI case of the spike and absent in case C), runs no startup migrations (measured, and that is the point), and resolves no model for the child, which the strict selection above replaces. No built-in extension loads by default either, which is what the child configuration decision below settles, while the standard coding tools stay whatever the role needs. Project trust is settled too, and it was never an unmeasured question: the bootstrap's child trusts the project unless Fusion says otherwise. Measured in case C, the child's bridge reported `projectTrusted: true`; source in 0.85.1, `SettingsManager.inMemory` defaults `projectTrusted` to true, while the CLI private-directory cases reported false, because their own settings set `defaultProjectTrust: "never"`. That value gates project settings and project-scoped resources, and each binding declares it `false` explicitly, as a decision about configuration loading rather than a sandbox over the child's tools or filesystem.

The API floor is demonstrated on 0.85.1 and nowhere else. The bootstrap uses six public constructors, `SettingsManager.inMemory`, `ModelRuntime.create`, `SessionManager.create`, `createAgentSessionServices`, `createAgentSessionFromServices` and `createAgentSessionRuntime`, plus `runRpcMode` (measured on 0.85.1). Three more public names carry the session and model checks, and the implementation depends on each of them: `parseSessionEntries` and `CURRENT_SESSION_VERSION`, which are what the session preflight reads a recorded transcript's entries and its own format version through, and `ModelRuntime.getError()`, which is the only public way to ask whether the model configuration loaded — a runtime built without it, or one whose `getError()` answers with something other than a string or `undefined`, is a compatibility failure that names the API and the shape rather than a call that runs on a configuration nothing checked. All of them are checked at startup: the exports and the statics before anything is constructed, `CURRENT_SESSION_VERSION` for its type, and `getError()` for its presence and its answer's shape. The wildcard peer dependency pins none of them, so check the exports and the protocol capabilities at child startup and refuse with an actionable error that names the version, rather than assume another Pi version behaves the same. Check what the adapter actually uses: the exports and the package version, then non-task RPC probes that the responses it depends on have the shape it reads — `get_state`, `get_available_models` and `get_available_thinking_levels` — with the remaining operations checked as they are safely used and their postconditions verified before any task prompt is submitted. Pi offers no capability handshake to ask instead, and none is invented here; `get_commands` lists the child's slash commands and answers nothing about this. "Only 0.85.1 was measured" is a reason to check what is used, not a version allowlist to enforce, and an API or operation that fails later stays a bounded expected failure path. The spike's one comparison run against a globally installed 0.87.1 covered the stock CLI only, so it says nothing about the bootstrap there. One more measured detail the bootstrap has to respect: the package publishes no `require` condition, so its entry resolves as ESM only.

Use LF-delimited JSON framing, correlated command ids, bounded diagnostics, and explicit handling of malformed output and unexpected exit. A successful prompt response acknowledges acceptance; it does not mean the task succeeded, and RPC emits it from a preflight callback before the turn runs (source, and measured in the lifecycle spike: a prompt whose bridge command failed still answered success). Failures also arrive as events of their own, `extension_error` among them, so read the event stream as first class rather than only the command replies. Finish only after `agent_settled`, inspect the final outcome, collect usage and checkpoint, then shut down the child. Measured why `agent_end` is not the place to stop: a retried call emitted `agent_end` with `willRetry` before `auto_retry_start`, an automatic compaction emitted `compaction_start` and `compaction_end` after an `agent_end`, an overflow recovery ran a summary and a second attempt inside the same call, and a queued follow-up ran its own turn, with exactly one `agent_settled` for the pair in each case, and nothing after it in a measured quiet window for the retry, the overflow recovery and the queued turn. Handle retries, compaction, and queued steering without prematurely completing the run.

Retain process-tree termination for cancellation and host shutdown, and add the portable best-effort policy of the process-cleanup decision below for Pi alone, as an opt-in the Pi caller passes: discover a run's descendants and signal them per pid as well as per group while the tree is still observable, including before a normal root exit, and skip a remembered pid whose ownership can no longer be established rather than signalling it blind. Both halves of that, the earlier discovery and the refusal to signal blind, reach the opting-in caller only; Claude's existing signalling and lifecycle are unchanged. Three measurements stand behind those rules: an abort with a steer and a follow-up still queued was followed by one further provider request carrying both, so `clear_queue` has to precede abort; a `setsid` grandchild of a Bash call outlived both an abort and a clean stdin shutdown, because Pi's cleanup is a process-group `SIGKILL` with a per-pid fallback and its graceful path is the same group kill (source), while an explicit per-pid signal from the harness did reach it; and a cancelled question is released inside the child by the forwarded abort signal with nothing written back for its request id, so the host must treat its own cancellation as that question's answer. Reject pending requests and release pending questions when the child exits or is cancelled.

## Child configuration and questions

Each role's Pi binding declares explicit extension and skill lists, which the bootstrap passes as constructor options with discovery off, so nothing is loaded from global settings, the project or packages; those lists plus the Fusion child bridge are all the child gets. Empty lists mean no optional extensions or skills. Provider extensions a role needs are listed the same way. Measured in the spike: the explicit lists kept a seeded user extension, project extension, skill, prompt template and package extension out of the child's command list, and an explicitly listed provider extension reached the child's available models on the bootstrap path, with no provider entry copied into any models file. Validate configured resources before starting work and report missing resources without silently loading alternatives. One caveat carries over from the spike: package resolution still runs with discovery off, and `PI_OFFLINE` is what stops a configured package from being installed at child startup (source, not executed there). The decisions below settle both halves of it without a new knob. A role lists existing local resource paths only, and an npm or git specifier, or a missing resource, has to fail rather than install a resource package at startup; discovery being off and the paths validating are not on their own a proof that it cannot, so what has to be verified is that the in-memory settings and the effective package sources leave the loader nowhere to install from. A coding task installing the project's own dependencies is untouched by that: it is a startup constraint, not a ban on Bash. `PI_OFFLINE` stays the user's, neither set for children nor cleared, and the helper and catalog behavior it gates belongs to the helpers-and-network decision.

Credentials and model configuration stay the user's, read in place and never created. `ModelRuntime.create`'s `modelsPath` reads the user's `models.json` where it is, and its `authPath` reads an existing `auth.json` where it is; measured, that left both files byte-identical through a whole run. What must not happen is opening a user auth path that does not exist: measured, a child pointed at a missing user `auth.json` created it as an empty file with mode 600, and the user's own next Pi startup then skipped its legacy auth migration, because that migration returns early once `auth.json` exists (source). The same file backend sits behind `ModelRuntime.create`'s `authPath` (source; untested for that entry point **when this was written**, which is step 1's evidence and is kept as it stood). That entry point has since been measured, and the rule below is what the measurement found rather than something it overturned: [docs/pi-auth-spike.md](pi-auth-spike.md)'s `A5` shows a call with no user auth file taking a private per-call path the SDK creates as `{}` at mode 0600 and disposal removes, with the user's own path never created, and the `P6` group of [docs/pi-config-write-spike.md](pi-config-write-spike.md) shows a real child reading and rotating an `auth.json` that does exist. What each of those qualifies, and what it does not, is task 4's status below. So the rule is narrow: read a user auth file only when it already exists, and otherwise give the child an explicit credential mechanism, either `ModelRuntime.create`'s credentials store or a Fusion-owned auth path inside the child's own directory, or fail with an actionable error. Never create a user configuration or auth file that does not exist. That is a rule about the user's own Pi configuration, not about the Fusion-owned subtree under the host agent directory, which the child writes by design, and not about what a coding task legitimately writes while it works. `AuthStorage` is not a public export in 0.85.1, and its deep import is not exported either (both measured), so credential handling goes through `ModelRuntime.create`'s options rather than a private module. Any design that resolves a key and hands it to the child through its environment or argv also puts a copy in Fusion's memory and in the child's process table (measured for the CLI's key flag: the value stayed off disk and stood in argv for the run). That copy is where it stops: a resolved credential is never written into a Fusion record, not the host session entry, not the history mirror, not the dashboard.

"The child writes nothing outside its own directory" is not a claim this proposal makes. Neither is the blanket promise these classes replace, that the child would "not edit the user's existing Pi configuration": that sentence is the one the configuration-write spike set out to test, and this is what survived it. Three different things are in play, and only the first is about the bootstrap:

- The child's own startup and settings commands. Measured: with the surfaces above owned by Fusion, they wrote nothing in the user's profile and nothing in the project, and the only watched write was the catalog cache in the child's own directory. The child also writes its session storage in the directory the bootstrap hands `SessionManager.create`, which the configuration-write spike did not watch; the lifecycle spike measured that half instead, creating, reopening and forking durable sessions inside Fusion-owned session directories, one per case inside its temp root and deleted afterwards. What stayed open was not whether the writes land there but the product policy for that storage's lifetime and location, which the storage decision below settles: a persistent children root under the host agent directory, durable per-project sessions that survive a host shutdown, a resume and a fork through the absolute session file each record names, and no automatic collection of any of it.
- An OAuth credential in an auth file that Fusion and the user intentionally share. Source, not tested, and with no fixture here: an expiring token is refreshed inside the credential store's modify call, which writes the rotated credential back into the user's file. That is the store working as designed, and it applies to any path that reads the user's `auth.json`. That case is decided rather than avoided: Fusion shares the user's existing auth in place, and the rotating write back into the user's file is explicitly authorized, as the auth decision below records. It is the one exception to the rule that only Fusion-owned configuration surfaces are written, it is still source rather than measured, and its rotation, locking and failure behavior owes fixtures before anything here claims it works.
- Whatever the child's tools, extensions, a `!command` credential helper in `models.json`, or Bash choose to write. Nothing here sandboxes that, on any of the options the spike compared.

Prevent the Fusion host extension from registering recursively in a child, including indirect package loading, using a child marker and an early guard in the host extension. Reject an explicit attempt to include the Fusion host extension in a role's resources. The child bridge is separate and does not expose tools for starting Fusion children. Contracts also prohibit launching nested Fusion sessions; the resource controls and registration guard are not a sandbox against arbitrary Bash execution.

Disable automatic prompt-template discovery as well; configurable child prompt templates are outside the initial scope. The project's instructions stay: measured for `AGENTS.md`, the project's context file reached the child's system prompt in every case of the spike, trusted project or not, while the user-level one reached only the child whose agent directory was the user's. Source: Pi tries `AGENTS.override.md`, `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md` and `CLAUDE.MD` in each directory and takes the first that exists, so a project holding both file names contributes only its `AGENTS.md` and never its `CLAUDE.md`. A Fusion-owned child directory therefore keeps the project's instructions and drops the user's global ones, which is what this plan wants. The rest of the system prompt is decided rather than assumed: Pi's own default base prompt, the project's normal instruction files through the resolution above, and the Fusion role contract, and nothing else. A project or global `SYSTEM.md` or `APPEND_SYSTEM.md` is never autoloaded as prompt configuration, which is a rule about configuration rather than a ban on a task explicitly reading such a file when the work calls for it. Discovery being off is not taken as proof that they are suppressed: the explicit supported configuration that does it, and a test showing a seeded pair of them reaching neither prompt, are what the child-configuration task owes, which is step 4's task 3. Source in a globally installed 0.87.1, which is why the rule has something to suppress: a normal trusted host loads the project's `SYSTEM.md` and `APPEND_SYSTEM.md` preferentially over the global ones, per filename. That is confirmed host behavior read on that version, not child policy already implemented. Reviews load the ask/review role's explicitly selected resources, not the source coding role's tools or skills; any provider extension needed for the selected reviewer model must be available in that configuration.

The child bridge registers `ask_orchestrator`, implemented through a blocking RPC UI input request. The parent maps its request id to the existing question queue and replies through `extension_ui_response`. The child half is measured in the lifecycle spike: the open request held the child with no provider request in a measured window, the answer arrived as the tool result correlated to the tool call id, a second reply for the same request id was silently dropped with no second tool result and no further provider request (source: the pending request is deleted on first use), two questions in a row each held the child in turn, and a steer queued while a question waited was delivered after the tool result as an ordinary user message at the start of the next turn. The run's tool list has to name the question tool, or the session's allowed tool names filter the bridge's registration out. Reuse exactly-once answer arbitration between host and user, foreground-to-background transition, and cancellation behavior; which side supplies an answer is Fusion's arbitration and the spike does not model it. Other supported extension dialogs must receive a defined response or an explicit error, never silently hang.

Contracts need backend-neutral language: use host/child vocabulary, remove the fixed three-model framing, and describe tools by capability or provide backend-specific instructions. Pi does not inherently provide Claude's `WebSearch` and `WebFetch`; advertise only tools actually configured. The existing `ask` role remains non-mutating by contract, including Bash. This is not a filesystem sandbox.

## Durable sessions and branching

Use backend-tagged session references. Claude keeps its session id and assistant checkpoint. Pi records its session file, session id, and durable entry checkpoint after the successful call has settled. That checkpoint is the leaf at settle, whatever kind of entry it is, and the lifecycle spike measured why the weaker rule is wrong: an automatic compaction appends a `compaction` entry as a child of the last assistant message and leaves it as the leaf, so a checkpoint taken as the last assistant message is that entry's ancestor, and restoring it drops the compaction off the branch and rebuilds the whole pre-compaction history. Missing backend fields in old records mean Claude.

The child's session navigation must restore the recorded checkpoint before sending another prompt, on every start. The stock RPC `fork` command branches from a user message and is insufficient for Fusion's completed-call checkpoint semantics. The bridge's command-context `navigateTree` and `fork` with position `at`, without summary generation, are now measured rather than merely available: the lifecycle spike restored recorded checkpoints, older checkpoints and post-compaction checkpoints with `navigateTree`, and measured that a `fork` at an exact entry contains precisely that entry's ancestry and that the two transcripts then stay byte-isolated from each other. Three measured details the adapter has to respect. The leaf is not persisted, so a reopened session sits at the file's last line, which after an abandoned call is that failure's own entry; restoration is mandatory and its postcondition is the proof. `SessionManager.open` on a path that does not exist does not fail, it binds a brand new session id to that path, and a checkpoint id absent from an existing file makes `navigateTree` throw inside a live session, so the child has to preflight the file and the checkpoint id and refuse before a session exists. And `fork` ignores a supplied session id: `createBranchedSession` generates its own (source), measured by passing one in and reading back a different one, so for Pi the record has to carry the id the child reports and a fork has no identity until the fork call returns. That is a change to `nextSession`'s contract, which today allocates a fork id up front, and it is the one record rule that cannot transfer unchanged.

Verify every navigation and fork by postcondition, never by a prompt going through. Read the session id and session file back from the child's state, the leaf id and branch shape from its tree, and the restored context from its entries, then require the recorded checkpoint to be the leaf and the context to be the one the record names. A prompt acknowledgement proves nothing about it: RPC reports a prompt as successful from a preflight callback, and a bridge command that failed surfaces as its own `extension_error` event. Measured in the lifecycle spike: an absent navigation target answered `Entry ... not found` and an absent fork target `Invalid entry ID for forking`, each as an `extension_error` carrying `extensionPath command:...`, while the prompt that carried them answered success, and the session id, session file, leaf and entry count were all unchanged. Treat a postcondition mismatch as a failed call. A refused operation therefore has three shapes to tell apart, not one: a thrown command reported as an `extension_error`, a postcondition that disagrees with the record, and a cancellation that is an ordinary `{ cancelled: true }` result with no error at all.

Required semantics:

- Normal continuation reads exactly the recorded context, including after a host restart.
- Host `/tree` restores the older child checkpoint and excludes later child turns. Measured on the child side: restoring an earlier checkpoint sent exactly that turn's context, the later turn appeared in neither the prompt nor the answer, and the durable file kept both continuations as sibling branches of the restored entry. The host's own record selection and its refusal to move the tree while a run is unfinished have no Pi child in them and stay unexercised.
- A forked host creates a separate child session from the recorded checkpoint on first use. Neither host subsequently writes the other's child transcript. Measured for the child half: the fork's entries were exactly the checkpoint's ancestry, entry for entry, its header pointed back at the parent session file, and each file's bytes were unchanged while the other took a turn, with neither payload carrying the other's prompt.
- Accepting a navigation or a fork needs two answers, in this order, before any task prompt: a non-cancelled operation result, and then verified postconditions. Measured in the lifecycle spike: an extension that answers `{ cancel: true }` to `session_before_tree` or `session_before_fork` makes the bridge's `navigateTree` and `fork` return `{ cancelled: true }` as an ordinary result, with the prompt that carried the command still answering success and no `extension_error` anywhere, and a cancelled fork leaves the child on the source session id and file with no branched transcript created, so a guard that only watches for errors walks straight past it. Nor is a postcondition that happens to hold permission to ignore `cancelled: true`: measured, a navigation to the entry that is already the leaf never reaches the hook at all and answers `{ cancelled: false }`, so "the leaf is the target" says nothing about whether an operation ran. A cancelled operation records nothing and submits nothing. Cancellation before a fork exists leaves the prior durable reference authoritative, which is the same shape as a failed resume below, and it does not touch the rule for a failure after a new fork identity exists.
- A call that failed after it resumed a recorded session records nothing, so the last successful checkpoint stays authoritative and the next call continues from it.
- A fork that failed after the child reported its new session records that session id together with the checkpoint it forked at, so the fork is not repeated and the context it branched from is what the next call gets.
- A new run that failed before any session exists records its handle alone, so the handle is never given out again and the next call to it starts a new session. Context fill is recorded only for a call that succeeded. Measured for Pi: a first call that reaches a provider error is not that case. The child had already reported a session id and the session file existed on disk, holding the failed prompt and an assistant entry with `stopReason "error"`, so the handle-only record applies only to a failure before the child reported a session at all. The handle-only record is written from the call's own outcome, so the failure has to arrive as one: a `backend.run` that throws skips `recordRun` today and writes nothing at all.
- Missing sessions or checkpoints cause an actionable error, never continuation from whatever context happens to remain. The child's preflight above is what makes that fail closed rather than silent. A record with no checkpoint is the one case the Claude backend takes a whole session: it resumes the whole session in the host that recorded it, and forks the whole session in a forked host, because `nextSession` carries a position only when the record has a checkpoint (source; the deterministic tests cover the checkpoint-less resume and the checkpointed fork, not the checkpoint-less fork). What either means for a Pi child is settled by the user-approved policy below: a Pi record naming a session and carrying no trusted checkpoint fails closed. The measurement is why, and it is a Pi behavior rather than the policy: reopening a failed new call's session whole and prompting again replayed the failed prompt, and the error entry stayed in the child's context while this provider adapter dropped it from the request, leaving two consecutive user messages. So a whole-session resume is not the neutral fallback for Pi that it is for Claude, and Fusion does not take one. A Claude record with no checkpoint keeps the behavior above unchanged.
- Keep `/tree` refused until every unfinished run has recorded its entry and delivered its result, across both backends.

Use supported Pi session APIs rather than hand-editing JSONL transcripts. Add migration tests for existing host entries and history files. Child transcripts remain durable independently of the optional Fusion history mirror.

### Recovery and identity transport

The three rules here are **user-approved policy** for the initial Pi backend, not a Pi behavior this project measured. They settle step 3's policy gate; the measurements they rest on stay in [docs/pi-session-lifecycle-spike.md](pi-session-lifecycle-spike.md). The host half of all three is implemented, as step 3's records, routing and recording, and is covered against a scripted backend. What is not implemented is the other half: no Pi child has ever produced one of these outcomes, because the adapter that would is step 4's and is not written.

**A first call that failed with an identity but no trusted checkpoint fails closed.** Such a record keeps the session file and session id the child reported, and the transcript stays on disk, so both can be inspected; that transcript can hold completed turns and finished tool work, so this is not a case of a failed prompt with nothing of value in it. What the policy declines is automatic context recovery: the next call for that handle refuses with an actionable error saying to start a new run under a new handle. No automatic whole-session resume, no silent reset, no same-handle reset feature and no salvage of the failed tip, initially. No recovery undoes what the failed call already wrote through the filesystem or its tools either. For `plan`, that guidance points at the existing `fresh: true`; no new or overloaded parameter is approved. A failure before any identity exists stays the handle-only case above, whose next call may start a fresh session for that handle. The policy covers Pi records only; do not broaden it to Claude's legacy checkpoint-less records.

**Only trusted checkpoints are restored.** A normal failed continuation records nothing, and the prior successful checkpoint stays authoritative. An error entry further down the physical session file does not make the whole session unusable: navigation restores the trusted entry and the failed later context is excluded from what the next call gets, which is the shape the older-checkpoint restore measured. A fork whose identity was verified and whose task then failed keeps the identity and session file the child actually assigned it, together with its fork-at checkpoint, never the failed tip. A fork or navigation cancelled before a verified new fork identity exists preserves the source record and sends no task. A fork-at checkpoint is trusted once the fork is verified, even though no call has yet succeeded in the new fork.

**Identity travels in structured returned outcomes.** Every outcome a Pi run produces, failure and cancellation included, carries whatever session reference has been verified: the session file and session id together, and the checkpoint when a trusted one exists, which for a successful call is the leaf at settle. A verified fork's identity and its fork-at checkpoint survive a later error or cancellation in that same outcome. The host writes the record in its existing finalization and recording step, from what the outcome carries, rather than from an id guessed before the call or a notification about the source session. No new early-session event and no two-phase API is the primary identity carrier, and there is no separate fork id to invent. The field layout and types were step 3 implementation work rather than an open policy question, and step 3 landed them; what is still missing is the Pi adapter that fills them from a real child.

Two limits on that last rule. The expected error and cancellation paths are the ones that have to return a structured outcome, because returning one is what lets the recording rules run at all: a `backend.run` that throws skips `recordRun`, so nothing durable is written, and this policy promises no recovery from an arbitrary unhandled throw or from the host dying mid-call. "Identity must not be lost to a throw" is a requirement on the Pi adapter's own exception and error handling, to be written once the shapes Pi actually produces are known. Claude's behavior is unchanged by all three rules.

## Step 4 decision record

These seven bundles are **user-approved policy** for the initial Pi backend, settled in one pass and written down before any step 4 code exists. Like the recovery rules above they are decisions rather than measurements, and their evidence base is thinner: the recovery rules rest on a spike that ran, while most of these rest on reads of the installed Pi and on what the earlier spikes happened to touch. None of them is implemented and none is measured as production behavior; the bounded tasks under step 4 below name the evidence each one still owes. They reopen nothing above: the identity, recovery and model-selection policies stand as written, and no Claude behavior changes.

**1. Process cleanup is portable best effort.** Linux, macOS and Windows are in scope from the outset, and what they get is a portable best-effort cleanup, not containment and not a guarantee over every descendant that ever existed. No `/proc` scanning, no cgroups, no Linux-only helper, no broad marker or orphan hunting across the machine, and no native supervisor requirement: the practical platform-native tree and group cleanup is what this uses. Discovery and cleanup happen while the tree is still observable, including before a normal root exit, rather than only as a sweep after the root is gone. All of this is Pi-only and opt-in: the earlier discovery, the normal-exit cleanup and the ownership rule below alike reach a caller that asks for them, and the Claude lifecycle, its signalling and its semantics are preserved exactly as they are. A change to the shared helper is something the Pi policy opts into, never a silent hardening of what Claude does. There is no blind late signalling of a remembered pid or process group for the opting-in caller: where ownership and identity cannot be safely established the process is skipped, and this document does not claim that checking an identity and sending a signal are one atomic act. A descendant that escaped its group or was re-parented may therefore be missed, and nothing here promises a warning for a process that was never discovered. A leftover descendant that *was* observed may be reported as a diagnostic warning; a failure to stop the run's own root process is an error rather than a clean success. All waiting is bounded.

Why an opt-in rather than a repair, as a factual baseline: `extensions/process-tree.ts` scans for descendants only while it is sending a signal, remembers bare pids and groups, and returns from `exited()` as soon as the root closes, with no later sweep. Those are pre-step-2 behaviors that the extraction moved unchanged rather than step 2 regressions, and this decision is not permission to change them for every caller now.

**2. Pi shutdown has a fixed order.** Stop accepting steers, then `clear_queue` before `abort`, because an abort with a steer and a follow-up still queued was measured to produce one further provider request carrying both. Wait for the settle and for outstanding responses under a bound. Resolve or reject every pending RPC request and release every pending question, since the host's own cancellation is what supplies the cancellation a child never answers back. Then close stdin for a graceful root exit, escalate termination under a bound if it does not come, and clean up the tree best-effort while it is still observable, and afterwards only where ownership is still known. Do not reflexively signal a stale pid once the root has exited. Expected failure and cancellation outcomes carry whatever identity has been verified, as the identity rule above requires; the original policy on an unexpected throw is unchanged, and nothing here mandates that the adapter never throws. Claude's abort order is untouched.

**3. Auth is shared in place, with rotation authorized.** The user's existing Pi auth is used where it lives, and an OAuth refresh writing the rotated credential back through Pi's credential store is explicitly authorized. A missing user auth or configuration file is never created; a missing auth is handled by a public SDK-supported mechanism instead, an explicit credential, an environment value, an in-memory store or a Fusion-owned credential path, or by an actionable failure. Fusion makes no default copy of OAuth refresh-token state. A resolved credential never reaches a Fusion record: not a host session entry, not the history mirror, not a dashboard record. A temporary runtime credential mechanism is not categorically forbidden. This is isolation and not a sandbox: the child's helpers, tools and extensions can write wherever the user's tools can, and the authorized OAuth rotation is the one exception to the rule that Fusion-owned configuration surfaces are the only ones written. One risk belongs with it: the package the bootstrap imports can differ from the host SDK that owns the shared auth, a child on 0.85.1 beside a host on 0.87.1, so preserving a credential format, a rotation and a lock that both can read is fixture evidence this owes too — not a hard version allowlist, and never a silent downgrade or a rewrite of the user's profile. Rotation, concurrent locking and failure behavior owed fixture verification, and that verification is now in: the store half in [docs/pi-auth-spike.md](pi-auth-spike.md) and the bootstrap half under *Task 4 stage* in [docs/pi-config-write-spike.md](pi-config-write-spike.md), both against throwaway profiles of literal dummy credentials and loopback endpoints on Linux and Pi 0.85.1 alone. What that says about the write, precisely: an existing entry's own **content** is what a rotation replaces — its access, its refresh and its expiry — while the file's other entries, its provider-specific extra fields and its 0600 mode come back as they were, and the transient adjacent `auth.json.lock` the credential store creates and removes is the SDK's own shared access to that one file, taken for a **read** as much as for a refresh, rather than a second authorized write. What is still not measured, there or here: a missing or replaced file as a race rather than a guarantee, durability across a crash mid-write, a compromised or stale lock, and a provider callback that drops a field it was handed. None of this is production behavior yet either way, because Pi is still not registered.

**4. The child's configuration is Fusion's, in memory.** Settings are in-memory and Fusion-controlled, with no automatic inheritance of global or project settings, and each binding declares `projectTrusted: false` explicitly — a decision about which configuration loads, not a tool or filesystem sandbox. The system prompt is Pi's default base prompt, the project's normal instruction files through Pi's own `AGENTS.md`/`CLAUDE.md` resolution, and the Fusion role contract. A project or global `SYSTEM.md` or `APPEND_SYSTEM.md` is never autoloaded as prompt configuration, which is not a ban on a task explicitly inspecting such a file as part of its work; nor is discovery being off assumed to suppress them, so the explicit supported configuration and its verification are owed. No built-in extensions load by default, while the standard coding tools stay whatever the role needs. Resources are explicit existing local paths only, as lists plus the child bridge, with discovery off. An npm or git package specifier, or a missing resource, must not cause a resource package to be installed at startup — and a coding task installing the project's own dependencies is unaffected, because that is a startup constraint rather than a Bash ban. What proves the no-install rule is the in-memory settings and the effective package sources leaving the loader unable to install, not local-path validation or discovery being off.

**5. Helpers are reused, the network is the user's.** The child runs with the ordinary `PATH`, with the host agent directory's `bin` appended to the *child's* `PATH` for read-only reuse, portably for case and delimiter, and with no mutation of the host's own environment. The child's `PI_CODING_AGENT_DIR` stays Fusion-owned, and stable: it is the one directory of decision 6 rather than a fresh one per call, so a helper Pi downloads once is there the next time instead of being fetched again. When those helpers are not available, a normal Pi `rg` or `fd` download into the Fusion-owned bin is permitted. The user's `PI_OFFLINE` is passed through exactly as set, neither forced nor cleared nor normalized, and no new helper policy knob is added. It is not one boolean: source in 0.85.1, the helper and package paths parse it as `1`, `true` or `yes`, while `ModelRuntime` checks whether the variable is present at all, so `0` or an empty string disables the catalog while helper downloads stay permitted. Fusion documents that as-is rather than papering over it with a normalization of its own. A model catalog refresh is allowed when online, by setting `allowModelNetwork` explicitly true where it is permitted, never forced and never required for a call to succeed when the model it wants is already available. Resource package installation stays forbidden at startup, which is a separate rule from helper downloads.

Source behind that bundle, read only and not executed, from a read of both installed versions: 0.85.1 and 0.87.1 ship an identical `tools-manager.js`; the interactive host attempts an `fd` and `rg` preload while the RPC and SDK entry points do not; `ensureTool` checks its own agent directory's `bin`, then `PATH`, and lazily downloads; the host never adds that bin directory to its own main process `PATH`, and `getShellEnv` adds it to the Bash tool's environment only; the host's bin path is computable from the public `getAgentDir` plus node's `path.join`, while `getBinDir` and the tools manager are private rather than public API; and `ModelRuntime.allowModelNetwork` defaults to false, with `PI_OFFLINE` gating the catalog as well as helper downloads, through the two different checks the nuance above describes. Reusing the host's bin through the child's `PATH` is a source-supported proposal on that reading and still needs real verification.

**Current policy for a concurrent first use, decided after that measurement failed.** The concurrency half of `P7` measured two children of one host on their first use of the same helper and found the loser told that the tool is unavailable. The route agreed at the time was an ownership or publication fix carried upstream to the SDK; that route was then **rejected by the user**, who accepted a small **Fusion-only retry** for this cold-cache edge case and approved its implementation. No SDK patch, dependency change, lock, warmup, preseed, sleep or new setting is part of it, and the SDK checkout is **left unmodified** — the earlier authorized clone was read for its source only, as [docs/pi-config-write-spike.md](pi-config-write-spike.md) records, with nothing edited, built or installed from it and no further access to it authorized by that record. What the retry is: `extensions/backends/pi-helper-retry.mjs` and its declaration wrap the public builtin `grep` and `find` definitions alone, so one model-issued tool call makes at most two underlying builtin attempts. It retries once, immediately, and only for an `Error` whose message is that tool's exact native helper-unavailable sentence; an unknown or reworded message, a non-`Error` value and any unrelated failure pass through unchanged, which makes this text-only compatibility rather than a root-cause classifier. One fixed credential-free tool update announces the retry, cancellation is checked before that notice and again before the second attempt, and a notice callback that throws propagates and prevents the retry. No task, prompt or session is replayed. A second attempt re-enters the **full native helper-acquisition path**, with the SDK's own fetch retries unchanged inside each attempt: it may cheaply reuse an install another attempt completed, and it may equally download again, contend with an attempt that has not finished, or fail for offline, network, permission or any other persistent reason. That is bounded best effort, not a repair and not a guarantee. The bootstrap builds those definitions through the public `createGrepToolDefinition` and `createFindToolDefinition` and passes them as `customTools` under unchanged names and schemas, behind the fixed safe SDK-compatibility refusals it already uses; a wrapper's metadata fields are copied from the factory's own definition, and nothing here claims the SDK's registry-origin label for such a tool is unchanged. The automatic retry applies **only when a call's `extensions` list is empty**: any named extension resource opts that call out entirely, which is what preserves an arbitrary override, late registration included, since a refresh applies an extension's registrations first and the custom tools last. It is not claimed that every possible call is covered — this build's role presets name no resources, and an internal explicit resource addition stays supported and simply gets no wrapper.

**6. Storage is persistent and uncollected.** Each host agent directory gets one stable child agent directory at `<host-agent-dir>/pi-fusion/children`, reused across Pi invocations rather than made per call, and that path is what the child's `PI_CODING_AGENT_DIR` names. Stability is the point: the persistent catalog cache and the helper bin live there, and a per-call directory would send Pi to download its helpers again into a fresh one every time. Per-project session storage sits below that root, durable and kept apart from those caches: it survives a host shutdown, a resume and a fork, through the absolute session file each record names. Ephemeral per-call input and configuration files are allowed as needed, somewhere else inside the Fusion-owned root, and are cleaned up on their own without touching the agent directory, the sessions or the caches. There is no automatic garbage collection, no session deletion, no cleanup command and no new storage override variable initially. Child transcripts persist independently of `PI_FUSION_HISTORY`, which mirrors the host's own records and is a different thing. What is Fusion-owned output is the configuration, cache, session and temporary state that Fusion and the bootstrapped runtime manage; it is not a claim about everything the child's tools write, which this is not a sandbox over. The user's existing `models.json` and `auth.json` and the host's helper bin are intentional read-only inputs, with the authorized auth refresh above as the one write back into them. Two things at that path are not the same and are not to be conflated: the authorized write is the rotating credential write into `auth.json` itself, which only a refresh performs, while the credential store also creates and removes a transient adjacent `auth.json.lock` around its access to that file — for a read as much as for a refresh — which is the SDK's own managed shared access to one file rather than a second write, a locking scheme of Fusion's or a credential store of its own.

**7. The runtime is a node process running our bootstrap.** A separate node process, taken from `PATH`, runs our plain-ESM bootstrap, which imports the installed public Pi SDK resolved from the bootstrap's own location. Not the stock CLI, never an in-process SDK child, and no provider client of our own. A missing or incompatible node, package, export, API or protocol produces an actionable error naming the version where one is available, with no automatic install and no silent fallback.    8. **Wire into the shared lifecycle, then register and document.** In `fusion.ts` and the pages under `docs/`: continuation, questions, steering, cancellation, background reports, cards, history and dashboard labels for a Pi run, with an end-to-end assertion that a Pi run's cancellation and shutdown take the opt-in cleanup path while a Claude run's take the one they take today. Registering the Pi backend by default for users, and the user-facing documentation saying it works, come last and only after the tasks above are verified, in-suite and by their named manual harnesses; until then the backend stays test-injected and this build still runs Claude only. Documentation for a behavior lands with the change that makes it true, and nothing claims the Pi backend ships before it does.

   What step 4 does not include: the `security` contract and binding, capability-based reviews and the remaining advanced integration are step 5's, the explicit live DeepSeek validation is step 6's, and no paid run of any kind belongs to step 4. It invents no new global configuration format, no user-configurable role system and no cleanup command.

5. Add the security contract and Pi binding; complete usage, context caps, capability-based reviews, history, and dashboard integration. Update contracts and documentation alongside each behavior change.
6. Run the full deterministic suite and typecheck, then perform a user-configured DeepSeek smoke run as an explicit live validation step.

## Acceptance and verification

Add `test/fake-pi.mjs`, following the fake-Claude pattern, for deterministic protocol tests without paid API calls. Cover success, streamed tools, two questions, competing answers, steering, cancellation with a Bash descendant, protocol errors, provider errors, retry/compaction before settled completion, premature process exit, an RPC that stops answering, and a root that fails to shut down inside its bound, because the bounded waiting the shutdown decision requires has to be tested against something that does not answer. The fake is named through the internal backend option the runtime decision settles, the same `fusion(api, { backends })` injection the scripted backend already uses: no user-facing variable, file or flag, and no CLI entry point.

Exercise the shared lifecycle against both backends: foreground/background transitions, global writer exclusion, shutdown, failed continuation, host restart, `/tree`, host fork, context handoff, and history restore. Test usage across multiple calls and partial failures for double counting.

Descendant termination has to be tested through the production discovery and cleanup path, never by handing the implementation the pids a fixture already knows. A fixture pid is an assertion oracle, and an emergency-cleanup oracle for the test's own `finally`; the set of processes to signal has to be the one the code under test found for itself. `test/child.test.ts`'s "aborting kills a detached grandchild that ignores SIGTERM" is already that shape for a Claude abort: the fake starts a real detached grandchild, reports its pid through a file, and the assertion is that the production path killed it. What is missing, and what step 4's first task adds, is the same shape for a descendant that was re-parented when its own parent died, for a root that exited normally instead of being aborted, and for the Pi backend. Those cases assert the approved best-effort guarantee rather than an absolute one, and the two halves are asserted differently. The ordinary owned tree and the normal root exit are the strong, unconditional cases: the fixture's own descendant has to be shown dead and the root shown stopped, killed by the set of processes the production path found for itself, so "it killed something" is never the assertion. The re-parented and escaped cases are conditional by design: cleanup where ownership is still provable, and a safe skip or a documented limitation where it is not, with a remembered pid whose identity cannot be established shown *not* signalled. No test asserts an unconditional orphan kill, none asserts a warning for a process that was never discovered, and none demands that a re-parented kill be guaranteed on every platform through new native identity machinery. A root that could not be stopped fails the run rather than reporting clean success. Every existing Claude case keeps asserting exactly what it asserts today, and the new behavior is reached through the opt-in only.

Verify the cancelled shapes of navigation and fork as their own cases, not as a variant of an invalid target: a cancelled operation must refuse the run before any task prompt is sent, keep the source session id, session file and leaf, create no fork transcript, leave the prior record authoritative, and produce no provider request. `test/spikes/pi-session-lifecycle.mjs`'s `row4-cancelled-operations` is the measured reference for what those postconditions look like on a real Pi child, including the positive control that shows the same guard permitting an uncancelled operation.

Verify security runs occupy the writer slot while running or waiting, can coexist with ask runs, record changed files, and qualify for manual and opt-in automatic reviews. Cover rejection of security on Claude and ultracode on Pi, and restoration of security records after a host restart. Role capabilities must preserve existing plan, implement, ask, and ultracode behavior.

Verify manual and automatic security reviews start fresh Pi ask sessions with the source run's resolved model and read-only review tools, including after history restore or a change to role defaults. Existing roles must retain their current reviewer selection. Review runs must not themselves trigger automatic reviews.

Verify different Pi roles resolve different configured providers/models through the same backend, explicit overrides take precedence, and continuation preserves its recorded model after role defaults change. Missing role model configuration must fail clearly without selecting another model.

Verify each Pi role loads only its declared extensions and skills plus the child bridge, even when global or project configuration contains additional resources. Cover empty lists, missing resources, explicitly listed provider extensions, and attempts to load the Fusion host extension directly or indirectly. Confirm the child never registers Fusion delegation tools and that reviews use their own resource lists.

Verify strict model selection: an exact `provider/model-id` in the child's available models is selected and reads back as selected; one that is not in them fails without a pattern match and without another model being chosen; a thinking level the model does not offer is refused rather than silently clamped; and a read-back that disagrees with the request fails the call before any task work. Verify the usage baseline across a continued run, a restored host and a host fork, so no earlier call is counted twice, that a model with no prices reports an unavailable estimate rather than zero, and that an unknown context after a compaction neither shows a stale share nor starts a handoff.

Verify the child's writable boundary, meaning the state the runtime itself manages: its settings, the catalog cache, the helper bin, the session directory, the per-call temporary files and the resource lists beside them all land in Fusion-owned locations, and the only paths into the user's profile are read-only inputs: the existing `models.json` and an `auth.json` that already exists under the auth rule above, and the host agent directory's helper `bin`, which the child reads through its own `PATH`. A missing user configuration or auth file is never created. A shared auth file is passed and its rotating write is authorized, and the transient adjacent `auth.json.lock` the credential store creates and removes around its access to that one file — for a read as much as for a refresh — comes with it, so this row is not a read-only claim about the user's auth path; this check fixes what Fusion configures rather than promising the shared file and its lock are never written, and it is not a sandbox: the child's helpers, tools and extensions can write where the user's own tools can. Verify the other direction too, that a resolved credential reaches none of Fusion's own records: no host session entry, history file or dashboard record holds it. That is the part the fake can prove; the profile and project measurement stays in the configuration-write spike's harness, which starts real Pi processes and therefore stays a manual run outside the `test/*.test.ts` glob.
