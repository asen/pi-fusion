# Runs, handles and background work

How a run is identified, how it survives resumes and forks, when it is handed off, and how the host manages one that runs in the background.

## Runs and handles

Every call to `fusion`, or to `claude` under its older name, belongs to a run, and every run has a handle such as `run-3`: one more than the highest handle on the host's current branch. A run is an ordinary session of the harness that ran it: a Claude Code session, or a Pi session. After each call the extension records a `pi-fusion` custom entry in the host session with the handle, the role, the backend the run went to, the host session id, and how that backend names the child's session again — for a Claude run its session id and a checkpoint, the uuid of the child's last assistant message in that call, and for a Pi run the structured reference below. The last entry for a handle on the host's current branch is the run's state.

`continue` with a handle resumes that run's session at its checkpoint and sends `task`, and `context` if given, as the next user message. The run keeps its role and its backend: a `backend` that names another one fails the call, and the `claude` tool refuses a run recorded on another backend and names the tool that can continue it; a `role` that differs from it fails the call. `model` and `effort` apply to the continued call as they do to a new one. Without `continue`, `implement` and `ultracode` start a new run, and `plan` continues the plan run with the last entry on the branch, so follow-ups can refer to the earlier agreement. `plan` with `fresh: true` starts a new plan run, and `continue` with the handle of an older plan run goes back to it. A `plan` call that would continue a run whose context has grown past its cap starts a fresh plan run instead (see [The context cap](#the-context-cap)).

Resuming the host session resumes its runs, because the entries are in the host's transcript. Going back with `/tree` takes the runs back too: the last entry on the older branch has an older checkpoint, and the next call for that run restores it in its backend's own way. A Claude run has Claude Code continue from that message on a new branch of the child's transcript, leaving the abandoned turns in the file but out of context. A Pi run is navigated there by Fusion's own control command inside the child, and the call goes on only once the session reads back as standing at that exact entry.

A call that fails after it resumed a session records nothing, so the next `continue` starts from the last successful call. A new run that fails before its backend reports a session records its handle with no session, so the handle is not given out again, and the next `continue` of it starts a new session. An entry without a checkpoint resumes the whole session on `claude` alone; a Pi entry with no trusted checkpoint is refused instead of resumed (see [Backends in a record](#backends-in-a-record)).

A forked host session has a different session id from the one in the entry. The first `continue` of a run in the fork, or the first `plan` call for the plan run, forks the recorded session at the recorded checkpoint into a new id and records that under the same handle, so the fork starts from a copy of the child's context up to that point and the two hosts stop sharing it from there on. How the copy is made is the backend's: a Claude child is resumed with `--fork-session`, while a Pi child is sent Fusion's own fork control command at the recorded checkpoint and the session id and file the child reports back are what gets recorded, accepted only after that new session reads back as standing at exactly that entry. A failed fork is recorded with the checkpoint it forked at. This covers both an in-session fork and `pi --fork <session>`. Nothing is copied at fork time; the fork happens on first use.

## Backends in a record

Each entry names the backend its run went to, and each backend's identity in a record is its own. A Claude entry keeps the session id and checkpoint it has always kept, flat. An entry that names no backend at all is a Claude run, which is what every entry written before the tags is. A `pi` entry keeps a structured session reference instead — the session id, the transcript file the session lives in, and a checkpoint only when one is trusted — together with the model and thinking level the child actually ran with, because a Pi continuation repeats that selection rather than resolving a model again against whatever is configured now. Both backends run here, so both kinds of entry are written.

A record this pi-fusion cannot act on keeps its handle and is refused rather than guessed at: an entry naming an unknown backend, a Pi entry whose reference is incomplete or mixed with loose fields, a Pi entry with no trusted checkpoint, a Pi entry with no model and level this host could repeat, and a Claude entry that keeps its session only in a structured reference and not in the session id that format carries are each kept for reading and never continued, and a new run never takes their handle. Wherever such a run's next step is offered — `fusion_control status` and `message`, `/fusion status`, and the lines about a run an earlier Pi process left — the refusal and what to do instead are what the host and the user are told, in place of an offer to continue the run. A refused entry is still its backend's latest plan run, so an implicit `plan` call stops at it instead of silently walking back to an older plan.

The recovery policy behind those refusals is in [the Pi backend plan](pi-backend-plan.md). In short: a call that failed after resuming records nothing, so the last successful checkpoint stays authoritative; a fork that failed or was cancelled after the child reported its new session records that session with the checkpoint it forked at, so the fork is not made twice, and it keeps it even when the call ended before it read back the model and level it ran with, which leaves a record that is kept for reading and not continued: nothing is guessed in place of what the child never reported, and new work goes to a new run; a first call that failed with a session but no trusted checkpoint keeps that session for reading and fails closed on the next call, because reopening it would replay the failed prompt; and a call that failed before the child reported anything records the handle alone, so the next call for it starts a new session. An outcome that names a session the run cannot have had — a resume that reports another session, a fork that reports the session it forked from, a settled call with no checkpoint or no selection — fails the run and writes nothing at all, leaving the earlier record as it was; the on-disk history keeps no identity for such a run either, because a reference the branch refused is not one this host verified.

Wherever the extension itself offers a way back to a child — the stats line of a result or a failure, the background report message, what `fusion_control wait` and `/fusion wait` hand back, and `/fusion status run-N` — a Pi run's transcript file is the reference the host accepted when the run returned, the same one the branch and the history keep. A run still going offers none, however complete the session its child claimed in progress looked, and neither does one whose backend threw or whose outcome failed a postcondition. A session kept for reading and not for continuing does name its file, because reading it is what is left of that run. A Claude run's line is what it always was: `claude --resume <session id>` for the flat id its child reported, live while the run is still going.

Entries written before handles existed carry only the plan session, under `consolidator` keys with a generation counter. The extension reads generation `g` as a `plan` run with handle `run-<g+1>`, so host sessions from before the change keep their plan session. A host started with `--no-session` keeps its entries in memory, so its runs last as long as the host does, but the Claude Code transcripts stay on disk like any other.

Claude Code stores the transcripts under `~/.claude/projects/<encoded working directory>/<session id>.jsonl`. If a recorded session has been deleted, or its checkpoint is no longer in the transcript, the next call to that run fails with Claude Code's error naming the session id or the message uuid; start a new run, or call `plan` with `fresh: true`.

A Pi child's transcript is the session file the record names, which is in Fusion's own storage under the host agent directory (see [where the pi backend writes](configuration.md#where-the-pi-backend-writes)). A Pi continuation fails closed rather than landing somewhere else: a record without both an absolute session file and a checkpoint this host trusts is refused before a child starts, with one sentence saying what to do instead, and a child that cannot reopen that exact session at that exact checkpoint — the file is gone, the checkpoint is not in it, or moving there would leave the session on another entry — fails the call and records nothing, so the last successful checkpoint stays the run's state. Start a new run, or call `plan` with `fresh: true`.

A continued `ask` run keeps its mode unless the call names another.

## Aborting a run

Aborting a foreground call with Esc stops the child, and how it is stopped is its backend's business. The tool fails with `<role> aborted while <activity>` either way.

A Claude child's process group, and the process group of every descendant, gets SIGTERM, then SIGKILL 5 s later to whatever is left, so a Bash command the child started dies with it. The extension spawns the child itself, through the SDK's spawn hook, because the SDK's own shutdown signals the child alone, 2 s after an abort, and escalates to SIGKILL only 5 s after that. A child that has finished its turn but is still running 2 s after the SDK is done with it is stopped the same way; that stop is not reported as a failure.

A Pi child is stopped over its own protocol first: the extension makes one observation of the descendants the child still owns, writes `clear_queue` and then `abort`, and stops the child with those descendants under one bounded cleanup. When that cleanup has something to report — a process nothing could stop, leftovers, a pipe still held, a deadline hit, descendants it could not even look at, or a stop this host could not verify — two things follow. That call's own storage directory is kept instead of removed, and one fixed sentence saying so is appended to what the run reports. The sentence is the backend's own words and carries no path, so a kept directory is found by the role name it is labelled with and the time it was made, read against the run in `/fusion status`, the history or the dashboard. A turn whose work read back whole is failed rather than reported `done` when its child's ending left any of that, because a run this host could not see the end of is not one it publishes a checkpoint from: its record stands at the session the run held before that turn.

## The context cap

A run that a host continues call after call keeps everything it read on the way, and that context is what each later call pays for. So each entry also records what the call's last model turn filled: the prompt tokens of that turn and the window they went into. Every call that would continue a run reads those from the last entry on the branch and compares them against a cap, 35% of the window by default. A `plan` call the host did not ask for by handle is the one case the extension acts on by itself: at or over the cap it starts a fresh plan run instead of continuing the old one.

The fresh run takes the next handle and gets the host's task with one section added: the replaced run's last report, capped at 32 KiB, between markers of its own, named as the plan agreed so far and marked as quoted data rather than instructions. What the run carries is the agreement, not the reading and the reasoning that reached it. The tool result opens with a line naming both handles and the share the old run had reached, so the host knows which run holds the plan now and that it can go back to the old one with `continue`. Later `plan` calls continue the fresh run, because its entry is now the last plan entry on the branch.

The handoff needs the replaced run's report, which it takes from this Pi process, or from the history when `PI_FUSION_HISTORY=1` kept it. When neither holds it, which is what a Pi restart without the history leaves, the call fails and says to restate the agreed plan in a `fresh: true` call or to continue the old run by handle. Nothing is handed off silently without the plan.

A `continue` call is never handed off. `fresh: true` is unaffected, because it starts a new run anyway: the host named the handle, and a run it names is the run it gets, however large that run's context has grown. Past the cap the call still runs and its result opens with a line that names the fill and what a fresh run would take instead: for `implement` and `ultracode`, a self-contained brief, because the work so far is in the work tree and the run's report names what it changed; for `plan`, a `fresh: true` call restating the agreed plan; for `ask`, a new `ask` run, which reads what it needs itself. The host decides. The extension does not refuse a `continue`, because `fresh` cannot go with `continue` and a refusal would leave a half-finished thread with no way to finish it in that session.

`PI_FUSION_PLAN_CONTEXT_PCT` sets the share, as a percentage between 0 and 100; `0` turns both off: every `plan` call continues the run as before, and no call warns about a context. It is read when Pi loads the extension, and a value that is not a percentage in that range leaves the default in place and says so once, the way the budget variables do.

The context fill is also shown where a run's numbers are: `context 400.0k/1.00M (40%)` in the stats line of every call that reported one, and `context 40%` in `/fusion status` and `fusion_control status`. A share that rounds to zero reads as `<1%`.
## Background runs

`background: true` works for every role. The call returns `<handle> started in the background; you get the report when it ends`, and the host can go on talking with the user. When the run ends, the extension sends the host a `pi-fusion-run` message with the handle, the final state, the report or the failure message, and the stats line. It calls `pi.sendMessage` with `triggerTurn: true` and `deliverAs: "followUp"`: Pi starts a new turn when the host is idle and queues the message as a follow-up when the host is in a turn. A run whose report reached the host through `fusion_control wait`, and a run `fusion_control cancel` stopped, send no message. A run the user cancels with `/fusion cancel` does send one, so the host hears about an end it did not order.

At most one run that is not an `ask` run is active at a time, foreground or background. A call that would start or continue a second one fails with an error that names the active handle, whichever backend either run is on. `ask` runs can be active next to it, because they do not change files. Continuing a run that is still active fails with an error that points to `fusion_control message`.

Esc stops a foreground run, as before, but not a background run. `fusion_control cancel` and `/fusion cancel` stop a background run the same way, and so does the end of the host session: quit, `/reload`, `/new`, `/resume` and `/fork` stop every active run before Pi tears the extension down. They also wait for a run that has ended but is still writing its entry, so the run keeps its handle and session in the host session. A new handle skips every handle this Pi process has used, so a run on one branch never takes the handle of a run that another branch still shows.

`/tree` is refused while any run is active, `waiting` and `ask` runs included, because the run's report and its `pi-fusion` entry would land on the destination branch. The refusal lasts until each run's `pi-fusion` entry is recorded and its report is delivered, which happens a moment after the run's state turns final, while the extension takes the last git snapshot. The extension shows a warning that names each such handle and role, marks a run whose state is final but whose entry or report is still pending as `finishing`, and cancels no run. Wait for the runs or cancel them with `fusion_control`, then run `/tree` again.

`fusion_control`, and `claude_control` under its older name, take `action`, `run` (a handle) and `message`. Both names act on every run of the Pi session, whichever tool and whichever backend started it:

- `status` without `run` lists every run of this Pi session with handle, role, model, state, elapsed time and open question. With `run` it adds the current activity, the tool call count and, for a run that is not an `ask` run, the files that changed in the work tree so far. It never returns the report.
- `wait` blocks until the run ends and returns its report or failure message, or until it asks a question and returns the question. Esc stops the wait; the run goes on.
- `message` answers a waiting run's question, or sends a steer to a running child. How a steer reaches the child is its backend's. For a Claude child the extension gives the SDK a queue of user messages as the child's input, not a single prompt, so stdin stays open while the child can still take a turn; it closes when a turn ends with no background task left, and Claude Code reads the steer when it next takes input. A Pi child is sent the steer over its own RPC protocol: the host's pushes are held in a queue until the turn's prompt has been taken, then sent one at a time with one attempt each and no retry, and a child that took it, a child that said no and a transport that would not send it at all are each accounted for. A message to a run that has ended sends nothing and is not an error, because a steer can race the run's end: the result gives the run's final state and a summary of its report, and says the host can continue the run with `fusion` and `continue`, or take no action.
- `cancel` stops the run and marks it `cancelled`. The failure text reads `<role> cancelled`, and when the backend has something to say about what stopping the run left behind it adds one fixed warning after it, such as `implement cancelled; cleaning up needs attention: leftovers; this call's storage is left behind`. The warning names what did not finish and whether a directory of the call is still there, in the backend's own fixed words: never a path, never what anything threw, never anything the child wrote. It is composed once, so the cancel reply, the `/fusion cancel` notice, which is shown as a warning then, and the report a wait, the background message, the history and the run the dashboard serves all carry that same one line, and no surface adds a second copy: for a run the host cancelled and whose backend carried such a warning, where that backend also left the same sentence as the run's last activity, the dashboard drops that line rather than showing it beside the failure. Every other ending keeps the activity its backend reported, a run the backend itself aborted included. A Claude run has no such warning, so its cancellation text is exactly what it always was; only the Pi backend composes one, and only when stopping that child left something to look at.

The user has the same controls without the host: `/fusion status`, `cancel`, `steer`, `wait`, `answer` and `review` act on the same runs (see [The /fusion command](fusion-command.md)). Each form that changes a run tells the host what the user did.
## Runs across Pi processes

The runs live in the Pi process. A run recorded on the branch by an earlier Pi process is not active; `fusion_control` says so, and `fusion` with `continue` continues it, on the backend the record names.

With `PI_FUSION_HISTORY=1` the extension also keeps the runs of each durable Pi session on disk, so a later Pi process on that session can show them. The extension writes a run when it starts, when its token count changes and when it ends, so a Pi process that dies mid-run loses little of it.

This writes project content to disk. When `PI_FUSION_HISTORY=1` is set, every run's prompt, report, failure text, changed-file paths and the session its backend verified are written under the history directory, which is `pi-fusion/history` under `~/.pi/agent`, or under `PI_CODING_AGENT_DIR` when that is set, or the directory `PI_FUSION_HISTORY_DIR` names. The directory is mode 0700 and each file mode 0600, one JSON file per Pi session, at most 100 records per file, 200 files and 1 MiB per file, with the oldest going first. They stay until you delete them, or until a cap drops the oldest to make room. Nothing is written while the variable is unset, and nothing is written for a Pi session that keeps no file of its own, such as a host started with `--no-session`. Texts are bounded: the prompt and the report at 32 KiB each, a failure at 4 KiB, and 500 changed paths per run. A run whose record alone would pass the 1 MiB file budget keeps its counts and gives up its path list, so one run never costs the file.

What that file keeps of a run's session is what the run returned and the host accepted, not what its child reported on the way: a record written while the run is still going names no session at all, and neither does one whose backend threw or whose outcome failed a postcondition, so a Pi process killed mid-run comes back with nothing to open. A session id, a session file, a checkpoint and a recorded model are kept exactly, never shortened to fit, and a value longer than 32768 characters is left out rather than cut, because a shortened path names another file and a shortened model another model. The `pi-fusion` entries on the host branch, which are what a continuation actually reads, are not bounded at all.

A record in that file belongs to a run on the branch only when the two name the same child: for a Claude run that is the session id, and for a Pi run the session id and the session file together, both verified, so a history record with another file, or with no identity where the branch has one, is not shown or reviewed as that run. A later Pi process on the same session reads that file and shows what it finds. `/fusion status` lists each earlier run under the live ones as `run-1 · implement · opus · done · earlier Pi process`. `/fusion status run-1` and `fusion_control status` with that handle give `run-1 (implement) ran in an earlier Pi process: done, 42s, 3 changed files`, the first 600 characters of its report or failure, and the lines that say to continue it with `fusion` and `continue run-1` and to review it with `/fusion review run-1`, each shown when that is possible: continuing needs the run's session on the host branch, and a review needs a run this working directory made. The session cost starts from what those runs spent, the dashboard lists them as restored, and a new handle never reuses an earlier process's. A run that was still going when its Pi process ended comes back as `aborted`. A forked host reads its ancestor session's file and never writes to it.

The files are written through a temporary file and a rename, and are never followed through a symbolic link. A file this pi-fusion cannot read costs one warning and never a run: a corrupt or foreign file is replaced by the next write, a file a newer pi-fusion wrote is left alone and read by nobody, and any other trouble, such as a directory this extension cannot make private, is reported once per Pi process and then kept quiet.
