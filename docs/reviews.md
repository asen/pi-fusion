# Independent reviews


`/fusion review run-N` starts an independent review of a run that has ended: an `ask` child in review mode, which the run that made the change never briefed. It runs the `ask` role, with that role's read-only tools and `contracts/ask-review.md` appended to its system prompt. The review is an ordinary run, so it takes the next handle, records its own `pi-fusion` entry, always runs in the background and reports through the background message. Its prompt names the run it reviews, tells it that the change sits in the working tree as uncommitted edits, points it at `git status --porcelain`, `git diff` and the files themselves, lists the paths the run changed, and carries the run's original task and report, each capped at 32 KiB. The task, the report and the failure go in as quoted data, each between markers of its own that the quoted text cannot close, and the prompt says that they are another agent's text: an instruction inside them is a finding to report, never one to follow, and the review changes nothing in the tree whatever they ask. It also says that the tree can hold work the run did not do, so the reviewer judges the listed paths and calls the rest out instead of reviewing it.

Which roles a review reads is role metadata rather than a list written into the reviewer: today it is `implement`, `ultracode` and `security`, and only a run of one of them that has ended `done` or `failed` with at least one changed file can be reviewed. A review of a run that is still active, of a `plan` or `ask` run — `run-1 is an ask run; only implement, ultracode and security runs are reviewed` — of a run that changed nothing, or of a run that was cancelled or aborted is refused with the reason, and so is a review while `PI_FUSION_BUDGET_LIMIT_USD` blocks new runs, or of a run an earlier Pi process made in another working directory. Reviewing the same run again starts another review; the run then points at the newest one. A run whose state has just turned `done` is still listing the files it changed, and `/fusion review` waits for that list rather than refusing the run as one that changed nothing.

The user sees `run-2 reviews run-1 in the background; its report arrives as a message`, and the host gets a followUp message that starts no turn. The links show on both runs: the review's line in `/fusion status` and `fusion_control status` reads `run-2 · ask · opus · done · background · 12s · review of run-1`, its report arrives as `Background run run-2 (ask, review of run-1) done.`, the reviewed run's tool result and end notice end with `run-2 reviews this run in the background; its report arrives as a message.`, its card header adds `reviewed by run-2`, and the dashboard lists Reviews and Reviewed by among a run's facts.

With `PI_FUSION_AUTO_REVIEW=1` the extension starts the same review on its own when an `implement`, `ultracode` or `security` run a delegation tool started ends `done` with changed files. It starts once per run, before the run's own report reaches the host, so the report and the tool result carry the review line. Only a run a delegation tool started gets one, so a review never reviews a review, and a failed, aborted or cancelled run never gets one. If the review cannot start, because the budget limit blocks it or for any other reason, the user is told why and the run reports as usual.

While fusion is off, neither `/fusion review` nor `PI_FUSION_AUTO_REVIEW` starts a review, and `/fusion on` starts none of its own (see [Turning fusion off](fusion-command.md#turning-fusion-off)).

## Which backend reviews a run

The reviewed run's role decides which backend reviews it, and a `security` run is the only one that is not reviewed by Claude.

An `implement` or `ultracode` run keeps the reviewer it has always had: a fresh Claude `ask` child in review mode, whichever backend made the run it reads. A run's own backend never moves that reviewer, so an `implement` run made on `pi` is still read by a Claude reviewer.

A `security` run is reviewed on `pi`, by a fresh `ask` child in review mode with `contracts/ask-review.md` and the Pi `ask` role's own tools — read, bash, grep, find and ls, with no edit or write tool. The model is the one that `security` run itself recorded having run with, taken exactly as recorded: a review of that work is worth no less than the work, and nothing about it is resolved again against whatever is configured now. `PI_FUSION_PI_ASK_MODEL` is never read for it, because the model is passed as the reviewer's own and a call's model wins over every variable. The thinking level is not inherited: the reviewer runs at this host's ordinary Pi `ask` level, which is `PI_FUSION_PI_ASK_EFFORT` when that is set and otherwise the child's own default, so a `security` run's level never sets its reviewer's. In every other way it is an ordinary run: its own handle, its own `pi-fusion` entry, a new session, the background, and the same links on both runs.

Nothing is guessed when the model is missing. A `security` run whose record holds no model it ran with — a run whose outcome this host refused, or whose backend threw before it reported one — is refused for review before a handle is taken, before the run is linked to a review and before any child starts, with `run-1 recorded no model it ran with, so no reviewer inherits one; review it yourself with fusion, role ask, mode review, backend pi and a model`. A reviewer the Pi binding will not bind for any other reason is refused the same way, with `run-2 would review run-1, and its reviewer could not be bound:` and the binding's own sentence after it, capped. A run an earlier Pi process left behind is reviewed on the model that run recorded in the history, not on anything this process is configured with.

A review run is an `ask` run, so it is not itself reviewable and no review ever reviews a review; `PI_FUSION_AUTO_REVIEW` reinforces that by starting one only for a run a delegation tool started.

What stands behind this: the deterministic suite drives the reviewer selection, both backends' reviewers side by side in one host, the level the Pi reviewer runs at, the missing-model refusal, and a history-held `security` run, all against a scripted in-memory backend that starts no process. No real Pi child has run a `security` role or reviewed one.
