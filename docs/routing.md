# Routing


The host model (GPT-6 Astra via the `openai-codex` provider) is the orchestrator. The tool guidelines injected into its system prompt ask it for two decisions. First, is the design unresolved: more than one viable approach, unclear requirements, a change to a shared contract or interface, or risk the host cannot bound by reading the code. If it is, the host calls `fusion` with role `plan` first; if the host can already say what to change, where, the acceptance criteria and how to verify it, it skips planning. The planner runs on the plan role's configured model; the host names another model only when you ask for one, which starts a fresh plan run that carries the plan so far. Second, the host sends all implementation to role `implement`, one bounded task at a time however complex or risky, and uses role `ultracode` only when you ask for it.

That leaves three routes: straight to `implement` when the design is settled; `plan` first and then `implement` task by task from the agreed plan; or `ultracode`, with or without `plan`, when you ask for it. The agreed plan's Route section recommends `ultracode` only when the goal says you asked for it.

Role `security` is outside those two decisions, and the guidelines say so: the host uses it when you ask for a security investigation, audit or fix, and never on its own judgement that some work looks security-sensitive — for that it uses `implement`, `ultracode` or `ask` with `mode: "review"`. The task is where the authorization comes from: a `security` task that says nothing about fixes reports findings and changes no application code, and one that authorizes a fix gets the smallest change that closes the finding. The role runs on `pi` alone and has no model until the session's settings give it one, so such a call needs a provider and model id in `model` or in its [setting](profiles.md), which the built-in configuration takes from `PI_FUSION_PI_SECURITY_MODEL`, and like `implement` it takes the single active file-changing slot.

Your explicit choice wins over the guidelines: ask for or skip planning as you like, and ask for ultracode to get role `ultracode`. A backend, model or effort you name goes in the `backend`, `model` or `effort` parameter; otherwise the host leaves all three unset and each role runs on this session's [configured settings](profiles.md), which the guidance states, rather than on model names fixed in the text. Left unset, a new run goes to the backend the session's settings give its role — `claude` for every role but `security` in the built-in configuration — while a `continue` stays on the backend its record names, `pi` included. A call that names the other backend runs there on that backend's legacy defaults, never on what is configured for the role's own backend. A role the session's settings disable is refused before anything starts, and the guidance recommends it nowhere. A role the named backend does not run, such as `ultracode` on `pi` or `security` on `claude`, is refused before a handle is taken or a child starts, with `role security does not run on the claude backend; use one of pi`. A role that runs on one backend alone needs no `backend` of its own: a `security` call goes to `pi` whether or not it names one. The compatibility `claude` tool has no `backend` parameter at all: it is this delegation with Claude forced, so it infers no other backend from a call or a record and refuses to continue a run recorded on `pi`, naming the tool that can.

When a task turns out to need a broader scope, or a design decision nobody has made, the `implement` child stops and reports that under Escalation instead of widening the task itself. The host then keeps what it changed and verified, and takes the design question to `plan` or the broader work to a new `implement` run.

The `ultracode` child has its own agents verify and review the work before it reports, and that report's Review section is the review step. Those agents are spawned and briefed by the implementer, so this is a self-review, not an independent one. The `implement` child reports its own verification only. For an independent review, the host calls role `ask` with `mode: "review"`, naming the change and what it must do; the implementer did not brief that child. A review `/fusion review` or `PI_FUSION_AUTO_REVIEW` starts is the same `ask` review run, on this session's `ask` settings (see [Independent reviews](reviews.md)). The host also uses role `ask` for a question about the code or its dependencies that would otherwise take it many file reads.

The guidelines also set how the host works with each child. The host writes each task and its context in plain prose, with the spaces between words kept. The child has not seen the host conversation, so each task must state the goal, the decisions, the constraints, the acceptance criteria and how to verify. The host checks each report against those criteria before the next task, reviews the change with role `ask` in `mode: "review"`, and reports a failed run's message instead of doing the task itself. It tells you the handle of each background run so you can follow it with `/fusion`, and it includes each run's resume command or session file, from the run's stats line, in its report. Children do not commit, and the host commits only when you ask.

The routes live in the tool guidelines and in the role contracts under `contracts/`. They are instructions to the models, not enforcement.

Where a call goes is settled before any backend binds a model for it: the backend, the role, the handle and the record it continues. A new run goes to the backend the call names, or to the backend the session's settings give its role; a continued run stays on the backend its record names. The model and effort a run binds come from the call, then from the run it continues, then from the session's settings for that backend, and a plan cap handoff keeps the planner's model as described in [the context cap](runs.md#the-context-cap). A `plan` call that names no handle continues the last plan run of the backend it routes to, so plan threads on different backends never run into each other, and a plan record this host refuses stops the call rather than sending it back to an older plan run.
